060 秒总述（先背这一段）

"MRO 是 Method Resolution Order，多继承下查找属性 / 方法时走的线性顺序表，存在 Cls.__mro__ 里——比如 D(B, C) 的 MRO 是 (D, B, C, A, object)。Python 3 用 C3 线性化算出它，三条规则：子类在父类前、多个父类按声明顺序、祖先的相对顺序不被颠倒（单调性）。它解决的是菱形继承的歧义——老式深度优先会让共同祖先 A 里的方法盖过 C 里的覆盖版本。MRO 决定两件事：属性查找的方向，以及 super() 的去向——super() 不是'父类'，而是'MRO 里当前类之后的下一个'，所以 D(B, C) 里 B 的 super() 会调到 C。协作式多继承靠它保证共同祖先只执行一次，Mixin 必须放左边才生效也是这个原因。"
这段为什么有深度：一次覆盖了「是什么 → 谁算的 → 解决什么问题 → 决定哪两件事 → 实战影响」，还主动点出"super() 不是父类"和"Mixin 放左边"这两个高频追问点。

1MRO 是什么？怎么查看？

一个类在继承体系里查找方法 / 属性时按顺序走的线性表，存在只读属性 Cls.__mro__ 里。
class A: pass class B(A): pass class C(A): pass class D(B, C): pass print(D.__mro__) # (<class 'D'>, <class 'B'>, <class 'C'>, <class 'A'>, <class 'object'>) print([c.__name__ for c in D.__mro__]) # ['D', 'B', 'C', 'A', 'object']

三种查看方式：Cls.__mro__（元组）、Cls.mro()（列表）、inspect.getmro(Cls)；help(Cls) 第一屏也会打印。

深度点：__mro__ 是只读的（实测赋值报 AttributeError: readonly attribute）；object 永远排最后——所有类最终都继承它，而"子类优先"规则保证它排在末位。

2为什么需要 MRO？高频

多继承下同一个祖先会被多条路径走到，必须有确定的、不歧义的查找顺序——这就是菱形继承问题。
class A: def f(self): return 'A' class B(A): pass class C(A): def f(self): return 'C' # C 覆盖了 A class D(B, C): pass print(D().f()) # C # 谁是 f 的来源？沿 MRO 逐类查 __dict__： print(next(c.__name__ for c in D.__mro__ if 'f' in c.__dict__)) # C
深度点：Python 2 的老式类用深度优先从左到右：D → B → A → C，会先撞上 A.f，把更派生的 C.f 盖掉——这正是"菱形继承的坑"。Python 3 全部新式类、统一走 C3：D → B → C → A，更派生的赢。所以"Python 按深度优先找方法"是错的（那是老式类）。

3C3 线性化是怎么算的？

L(类) = 类自己 + merge(各位父类的 L、以及父类列表本身)；merge 每次取"第一个列表中第一个不出现在其他列表尾部的元素"。
# 已知：L(A) = [A, object]，L(B) = [B, A, object]，L(C) = [C, A, object] # 求 D(B, C)： L(D) = D + merge( [B, A, object], [C, A, object], [B, C] ) # 候选 B：没出现在任何列表尾部 → 取走 = [D, B] + merge( [A, object], [C, A, object], [C] ) # 候选 A：出现在 [C, A, object] 的尾部 → 跳过；候选 C：可以 → 取走 = [D, B, C] + merge( [A, object], [A, object] ) = [D, B, C, A, object]
  • 子类优先：每个类的 L 都以自己开头；
  • 声明顺序：多个父类按书写顺序进入候选；
  • 单调性：某类在祖先里的相对顺序不能被合并打乱——"A 出现在别的列表尾部"就意味着还有更派生的类没排到 A 前面，必须先跳过它。
深度点：手写一个二十行的 merge 递归版算 L(D)，结果与内置 D.__mro__ 逐项一致（实测 ['D','B','C','A','object']）——面试被要求"手推一下"时按上面那个例子讲就够。

4为什么 super() 不是"父类"？最高频

super() 的语义是"MRO 里、当前类之后的下一个"，单继承时才恰好等于父类。
class B2(A2): def f(self): print("B2"); super().f() # 不是调 A2，而是调 C2！ class C2(A2): def f(self): print("C2"); super().f() class D2(B2, C2): pass print([c.__name__ for c in D2.__mro__]) # ['D2', 'B2', 'C2', 'A2', 'object'] D2().f() # B2 → C2 → A2 ← B2 里的 super() 跳到了 C2
深度点：① super() 是"按 MRO 走，不按继承树走"——这就是协作式多继承的基石；② 零参 super() 依赖编译器为类体生成的 __class__ 单元格，只在类体内定义的函数里可用；类外动态加的方法要显式写 super(C, self)；③ super(C, self) 的语义同样是"从 C 之后开始找"，不是"找 C 的父类"。

5协作式继承：__init__ 为什么每个类只跑一次？

因为每层都调 super().__init__() 时，走的是同一条 MRO，每个类在链上只出现一次。
class A3: def __init__(self): print("A3") class B3(A3): def __init__(self): print("B3"); super().__init__() class C3(A3): def __init__(self): print("C3"); super().__init__() class D3(B3, C3): def __init__(self): print("D3"); super().__init__() D3() # D3 → B3 → C3 → A3 ← 共同祖先 A3 只执行一次
深度点：不调 super() 就没有"协作"——父类的 __init__ 根本不会执行（断链）；而如果两条路径各自显式调用共同祖先，A3 会执行两次——那才是菱形继承的经典 bug。Django CBV、Pydantic 模型、各种 Mixin 体系全靠这条链：每层都调、只调一次、共同祖先收尾。

6什么时候报 "Cannot create a consistent MRO"？

基类顺序互相矛盾、无法同时满足所有约束时，类定义当场报错（import 期 fail-fast）。
class D(B, C): pass # 要求：B 在 C 前 class E(C, B): pass # 要求：C 在 B 前 class F(D, E): pass # ❌ 两个要求冲突 # TypeError: Cannot create a consistent method resolution # order (MRO) for bases B, C

处理办法：调整基类顺序 / 用组合代替继承 / 拆掉不合理的多继承结构。

深度点：报错信息会点名冲突的基类（这里是 B, C）——排错时先看这两个谁该排在前面；这类错误在定义类时就抛出，不会等到运行。

7Mixin 为什么要放左边？

属性查找按 MRO 从左到右，写在右边的类永远排在后面，会被左边的实现覆盖到"轮不到"。
class Base: def dispatch(self): return 'Base' class Mixin: def dispatch(self): return 'Mixin→' + super().dispatch() class View1(Mixin, Base): pass class View2(Base, Mixin): pass print(View1().dispatch()) # Mixin→Base ✅ print(View2().dispatch()) # Base ❌ Mixin 根本没轮到 # View2 的 MRO: (View2, Base, Mixin, object)
深度点：① class MyView(LoginRequiredMixin, View) 这种写法里的顺序是有语义的，调换就失效（Django CBV 排错日常）；② Mixin 里之所以总写 super().method()，就是要把请求沿 MRO 继续传给右边的基类，否则链断。

8MRO 还会牵连哪些考点？

  • 属性查找：实例 __dict__ → 沿 MRO 逐类找（数据描述符优先级最高）；"这个属性哪来的"就用 __mro__ 逐类查 __dict__；
  • 别和 isinstance 混：isinstance / issubclass 看的是继承关系（还包含虚拟子类），和 MRO 顺序是两回事；
  • 元类：多继承时"最派生元类"的判定同样沿继承链进行，metaclass conflict 就是这个规则的表现（详见 元类速答）；
  • 排错三件套：Cls.__mro__ 看顺序、inspect.getmro() 取元组、help(Cls) 第一屏就是 MRO。

9常见追问（快答）

Q：__mro__ 和 mro() 有什么区别？→ __mro__ 是只读元组属性；mro() 是类方法、返回列表，语义等价；另有 inspect.getmro()。
Q：能改 __mro__ 吗？→ 不能，只读（实测 AttributeError: readonly attribute）；要换顺序只能新建类。
Q：为什么 object 总在最后？→ 所有类最终都继承它，而"子类优先"保证它排末位。
Q：MRO 里会有重复的类吗？→ 不会，C3 保证每个类只出现一次——这正是菱形继承里共同祖先只执行一次的原因。
Q：单继承也有 MRO 吗？→ 有，就是一条链 (C, B, A, object)，只是没有歧义。
Q：老式类和新式类的差别？→ Python 2 老式类用深度优先（有菱形坑），新式类和 Python 3 全部新式类统一用 C3。

!减分点清单（别踩）

  • 说"Python 按深度优先查找方法"——那是 Python 2 老式类，Python 3 是 C3；
  • 说"super() 就是调用父类"——是 MRO 上的下一个，D(B, C) 里 B 的 super() 是 C；
  • 说"多继承就是按声明顺序依次找"——还要满足单调性，矛盾时直接报 MRO 冲突；
  • 把 isinstance（继承关系）和 MRO（查找顺序）混为一谈；
  • 写 Mixin 放右边，然后困惑"为什么我的方法没生效"；
  • 每层不调 super() 导致协作链断掉，却以为是 MRO 算错了。
