060 秒总述（先背这一段）

被问到"讲讲元类"时，不要直接开始讲 `type vs object`，先给出这段结构完整的总述，再按面试官兴趣展开：

"元类就是创建类的类。Python 里类也是对象，默认由 type 创建，class 语句本质是 type(name, bases, namespace) 的语法糖。自定义元类继承 type，重写 __prepare__ / __new__ / __init__ 就能在类创建过程中改写它的命名空间；重写 __call__ 还能拦截实例化。它存在的价值是让机制在类定义那一刻自动生效——注册、字段收集、契约校验，使用者只写声明、漏不掉。代价是复杂度和元类冲突，所以能不用就不用，PEP 487 的 __init_subclass__ 覆盖了大多数需求；但需要'创建期改写类'或'控制类对象协议'的地方，元类至今不可替代，比如 Django 的 ModelBase、Pydantic 的 ModelMetaclass、abc.ABCMeta。"
这段为什么有深度：一段话覆盖了「是什么 → 怎么实现 → 为什么需要 → 什么时候别用 → 谁在用」，而且主动说出替代方案和真实库——面试官立刻知道你不是背教程的。

1什么是元类？

普通类创建实例，元类创建类。默认元类是 type。

推理三步：一切皆对象 → 类也是对象 → 类由"某个类"创建，那个类就叫元类。

class Dog: ... print(type(Dog)) # <class 'type'> → type 创建了 Dog # 等价写法（class 就是它的语法糖）： Dog = type('Dog', (object,), {'bark': ...})
深度点：与其背"元类能做什么"，不如记住它接管的是类的创建协议——type(name, bases, namespace) 这三个参数就是元类 __new__ 的前三个参数。
追问：type 的三个参数是什么？→ 类名（str）、父类元组（tuple）、类体命名空间（dict）。

2type 和 object 什么关系？高频

两个维度：type 回答"谁创建我"，object 回答"我继承谁"，互不干扰。
  • 创建维度：type(Dog) is type，连 type(object) is type、type(type) is type；
  • 继承维度：Dog.__bases__ == (object,)，type.__bases__ == (object,)，object.__bases__ == ()。
深度点："type 创建 object、type 又继承 object、type 还创建自己"看似循环，实际是创建链与继承链的交叉。答"创建看 type()、继承看 __bases__"就破题了。
追问：元类自己是谁创建的？→ 也是 type；自定义元类 class Meta(type) 的元类仍然是 type。

3类的创建流程？__new__ 的四个参数？高频

__prepare__ → 执行类体 → __new__ → __init__；参数是 mcs, name, bases, namespace。
class Meta(type): def __new__(mcs, name, bases, namespace, **kw): # ↑元类自己 ↑类名 ↑父类元组 ↑类体字典（此时类还不存在） namespace['_x'] = 1 # 创建前：唯一能改 namespace 的地方 return super().__new__(mcs, name, bases, namespace)
  • __prepare__：类体执行前，决定类体往哪个命名空间写（enum 用它边定义边查重）；
  • __new__：创建过程中，能增删改 namespace——元类威力最大的位置；
  • __init__：类对象已存在，只能读、setattr 和做副作用（注册、校验）；
  • 实例化是另一条链：元类 __call__ → 类的 __new__ → 类的 __init__。

顺带说清：namespace（命名空间）是什么、存了什么？

  • 它就是一个字典：类体里每写一个名字（x = 1、def run、文档字符串），都是往这个 dict 里写一条 key → value；类体执行前由 __prepare__ 提供容器（默认空 dict），执行完整个字典交给 __new__。
  • 里面存两类东西：① 你声明的属性、方法、注解（__annotations__）；② 解释器自动加的元数据——__module__（定义在哪个模块）、__qualname__（限定名）、有文档字符串时的 __doc__。
  • 创建完成后去哪了：被固化进类的 __dict__（只读 mappingproxy），此后属性查找都在它里面进行——所以想改成员，只能在 __new__ 里改"可变的那份"。
  • 不是元类专属概念：模块有模块命名空间（模块的 __dict__）、实例有实例命名空间（实例的 __dict__）、函数调用有局部命名空间——本质都是"名字 → 值"的 dict，Python 的 LEGB 变量查找就是按这些 dict 依次找。
class Meta(type): def __new__(mcs, name, bases, ns, **kw): print(dict(ns)) # 看内容：类体里写的一切 + 自动元数据 ns['_extra'] = 1 # 此刻它还是普通可变 dict，随便改 return super().__new__(mcs, name, bases, ns) class User(metaclass=Meta): name = 'x' # 近似输出（3.13 起还会多出 __firstlineno__、__static_attributes__）： # {'__module__': '__main__', '__qualname__': 'User', 'name': 'x'}
记忆点：元类 __new__ 手里是可变的 dict，__init_subclass__ 手里是只读的 cls.__dict__——这一"可变 / 只读"之差，就是两者能力差的根源。
深度点：super().__new__（即 type.__new__）内部会顺带触发属性的 __set_name__ 和父类的 __init_subclass__——所以 super().__new__ 的前 / 后，就是"类未创建 / 已创建"的分界线。

4元类里 __new__ 和 __init__ 怎么分工？

__new__ 管"造"，能改 namespace；__init__ 管"善后"，只能读和 setattr。

要注入、替换、删除类成员 → 必须放 __new__ 且写在 super().__new__ 之前；注册、校验、加缓存 → 放 __init__，别忘了调用 super().__init__。

深度点：类创建完成后 cls.__dict__ 是只读的 mappingproxy，没法像 dict 一样改——这就是"改方法必须趁 __new__"的硬原因，也是元类与 __init_subclass__ 的分水岭。
追问：为什么很多教程只在 __new__ 里写逻辑？→ 重活集中在能改 namespace 的阶段，__init__ 只做与类创建无关的收尾，职责更清晰。

5元类能拦截"实例创建"吗？

能。类本身是元类的实例，Demo() 先经过 type(Demo).__call__，也就是元类的 __call__。
class SingletonMeta(type): _instances = {} def __call__(cls, *a, **kw): if cls not in cls._instances: cls._instances[cls] = super().__call__(*a, **kw) return cls._instances[cls]
深度点：① 它作用于该类及其子类的每次实例化，属于热路径，有 Python 层开销；② 多线程下有竞态，要加锁；③ __init__ 只在第一次执行，后续调用被静默忽略；④ Python 里模块级对象天然是单例，实际项目通常不必用元类做单例——主动说出这点是加分项。
追问：除了单例还能干嘛？→ 实例缓存 / 对象池、创建审计、限制直接实例化（只允许工厂方法）。

6元类、__init_subclass__、装饰器怎么选？高深度题

分水岭：要不要介入创建过程 / 控制类对象本身；不要的话，一律优先轻方案。
手段生效时机能做什么 / 不能做什么
类装饰器类创建后改造类；需逐个书写，可能漏
__init_subclass__子类创建后（父类被通知）注册、校验、统一设置属性；改不了 namespace
描述符 __set_name__类创建时（属性归属确定）属性级：注入字段名；管不了整类
元类创建过程中 + 类对象层__prepare__、改 namespace、__call__、__instancecheck__——只有它能做
深度点：面试里大量"元类做自动注册"的答案其实用 __init_subclass__ 就够了，"给字段注入名字"用描述符 __set_name__ 才是官方设计（下一题给出完整写法）。能说出这两句，直接区别于"只会背元类"的候选人。

7__init_subclass__ 怎么用？必会

在父类里定义 __init_subclass__(cls, **kwargs)，任何子类被创建后都会自动调用——定义在父类，触发在子类。
REGISTRY = {} class BaseTool: def __init_subclass__(cls, tool_name=None, **kwargs): super().__init_subclass__(**kwargs) # ① 自己不消费的 kwargs 继续传递 key = tool_name or cls.__name__.lower() cls.tool_name = key # ② 类已建好，直接 setattr REGISTRY[key] = cls # ③ 注册：子类定义即生效，漏不掉 class Search(BaseTool, tool_name='search'): # 类关键字参数直达钩子 pass print(REGISTRY) # {'search': <class 'Search'>}
  • 它是隐式类方法：不用写 @classmethod，第一个参数固定是新建的子类（不是定义它的父类），可以正常 cls.xxx、setattr；
  • 必须调 super()：super().__init_subclass__(**kwargs) 是协作式多继承的规矩，不调的话兄弟基类的钩子不会执行；
  • 类关键字参数从这里进：class Search(BaseTool, tool_name='search')，自己消费一部分，剩下的原样传给 super；
  • 能力边界：拿到的是"已创建"的类——注册、校验、setattr、包装方法都行；但改不了 namespace、也拦不住实例化，这两件事才是元类的地盘。
深度点：① 只对子类触发，定义它的那个类自己不会触发；② 时机上 type.__new__ 先给各属性调 __set_name__、再调父类的 __init_subclass__——所以在钩子里拿到的描述符已经带好了字段名；③ 在钩子里 raise TypeError，可以直接禁止别人继承这个类。
追问：它和元类的 __init__ 有什么区别？→ 时机几乎相同（都是"类已建好、只能 setattr"），但元类钩子属于元类（一个类只能有一个元类、且沿继承链传染），__init_subclass__ 属于父类——不引入元类冲突，多个父类还能叠加执行。

追问延伸：改 namespace 和 setattr 到底差在哪？

对普通属性两者完全等价（最终就是同一个类）；差别只在"创建过程中会被读一次 / 触发一次"的东西上。
  • __slots__：定实例的内存布局——只有改 namespace 有效，类建好后再 setattr 不生效；
  • __set_name__：只对"创建时就存在的属性"回调一次——事后 setattr 塞进去的描述符永远拿不到名字；
  • 创建期快照：如 abc 的 __abstractmethods__ 在创建时算好，事后补抽象方法不会重算、拦不住实例化；
  • 创建期钩子：父类 __init_subclass__ 看得到 namespace 的改动，看不到创建完成后的 setattr；
  • 覆盖顺序：namespace 是最早的一版，之后任何 setattr 都能覆盖它，反过来不行。
一句话判断：要影响"创建过程本身"（内存布局、回调触发、创建期机制看到的内容）→ 必须用元类改 namespace；只是普通属性 / 方法 → __init_subclass__ 里 setattr 或类装饰器就够了。

8什么时候"必须"用元类？

只有两类：① 创建期改写类（__prepare__ / 改 namespace）；② 控制类对象协议（__call__、__getattr__、__instancecheck__ / __subclasscheck__）。
  • 改 isinstance 语义：abc.ABCMeta 的虚拟子类（register() 后 isinstance 为真）只能靠元类的 __instancecheck__ / __subclasscheck__；
  • 类体执行期介入：enum 用 __prepare__ 返回自定义命名空间，在成员定义写入的瞬间检测重名；
  • 类级属性兜底：元类的 __getattr__ 只拦"类对象上找不到的属性"，实例属性查找不经过它（这个边界很容易答错）。

9metaclass conflict 是什么？怎么解决？

子类的元类必须是所有父类元类的（非严格）子类；两个不相关的元类混用 → TypeError: metaclass conflict。

解法是组合元类：

class CombinedMeta(MetaA, MetaB): # 同时继承双方 pass class C(A, B, metaclass=CombinedMeta): # ✅ pass
深度点：这就是元类"传染性"的代价——一个基类上了元类，整条继承链都被绑定。自己写元类永远用 super().__new__，不要硬编码 type.__new__，否则组合元类的协作链会断。
追问：元类会继承吗？→ 会，父类指定了元类，子类不写 metaclass= 也自动沿用。

10生产中的实际用途？点出真实库加分项

凡是"类定义即生效"的框架机制都是元类：声明式 DSL + 不可绕过的不变量 + import 期 fail-fast。
库 / 模块元类干了什么
Django ModelBase收集字段、处理 class Meta 选项、生成 _meta、注册到 app registry
Pydantic ModelMetaclass把注解收集成校验器（V1 / V2 都在用，V2 只是校验核心下沉到 Rust）
DRF SerializerMetaclass / Django forms把声明字段汇总成 _declared_fields / 表单字段表
abc.ABCMeta抽象方法强制 + 虚拟子类与 isinstance 语义
enum.EnumType__prepare__ 在类体执行期拦截成员定义、查重名
六大模式一句话版：自动注册、ORM 字段收集、接口契约（定义期 fail-fast）、AOP 织入、声明式路由 / 文档收集、配置校验——回答时点到真实库名，可信度立刻不同。

11为什么现代 Python 建议"少用"？

深度控制换来的是可读性、互操作和冲突成本，而 PEP 487 给了更轻的替代。
  • 成本：控制流藏在元类里、"魔法属性"难追溯；元类传染性 + conflict 风险；IDE / 类型检查器识别差；类对象层钩子在热路径；
  • 替代：PEP 487 新增 __init_subclass__ 和 __set_name__，官方动机就是让多数"元类诉求"有轻方案；
  • 证据：SQLAlchemy 2.0 的 DeclarativeBase 采用"元类 + __init_subclass__"混合——属性拦截留元类，模型构建流程下移。
深度点："少用"≠"没用"。Django / Pydantic 至今保留元类，因为"创建期改写类"无可替代；结论句：能不用就不用，需要时它是唯一解。（可以引用 Tim Peters：不确定是否需要元类的人，就是不需要。）

12现场设计题：实现一个带校验的 ORM / 插件注册，你怎么做？

先给轻方案，再说明"什么条件下升级到元类"——这个顺序本身就是加分项。
  • 注册 → 父类 __init_subclass__ 里写 registry，子类定义即注册；
  • 字段名注入 → 描述符实现 __set_name__；
  • 汇总 / 表名推导 / 校验 → 先用 __init_subclass__ + setattr；
  • 升级为元类的条件 → 需要在创建前改写 namespace、或同时处理类级选项（Django 要处理 class Meta 选项 + 注册 + _meta，所以才用 ModelBase）。
深度点：面试官想听的不是"我会写元类"，而是"我知道何时不该用"。给出"轻方案 → 升级条件"的决策路径，比直接甩元类代码高级得多。

!减分点清单（别踩）

  • 说"元类继承自 object"——元类继承 type，是 type 继承 object；
  • 混淆两条链：类创建走 __new__ / __init__，实例创建走元类 __call__；
  • 说 __init__ 里能改 namespace——类已固化，只能 setattr；
  • 只会背"ORM / 单例"，说不出 __init_subclass__、__set_name__ 这些替代方案；
  • 说"Pydantic V2 已经不用元类了"——事实错误，V2 仍是 ModelMetaclass；
  • 把元类单例当成最佳实践——模块级实例更简单，说得出这点反而加分。
