0开篇：旧 Chain 方案的三个痛点

Workflow 引擎不是凭空设计的——它诞生于旧 Chain 模式（wiki_chain.py）的三个真实痛点：串行瓶颈（N 个文件 = N 次串行 LLM 调用）、流程硬编码（三步固定链改不动）、数据传递脆弱（全靠 {previous} 纯文本拼接）。下面逐条展开。

痛点一：wiki-writer 逐文件串行

旧 Chain 的 wiki-writer 阶段，一个 commit 改了几个文件就要串行调用几次 LLM：

场景旧 Chain 耗时Workflow 优化后
commit 改 1 个文件≈ 1 × 单次 LLM 延迟（~15s）≈ 1 × 单次 LLM 延迟
commit 改 10 个文件≈ 10 × 单次 LLM 延迟（~150s）≈ 1 × 单次 LLM 延迟（~15s，全部并发）
commit 改 30 个文件≈ 30 × 单次 LLM 延迟（~450s）受 Semaphore 限流，但仍远快于串行

根因是 ChainStep 列表按顺序执行，每个 step 的 {previous} 只能是前一歩的结果字符串——没有并发能力。

痛点二：流程编排硬编码在 Python 中

旧 Chain 模式 — 流程与代码耦合
# wiki_chain.py 中硬编码的三步链
chain_steps = [
    ChainStep(agent="diff-analyzer",  prompt="..."),
    ChainStep(agent="wiki-planner",  prompt="..."),
    ChainStep(agent="wiki-writer",   prompt="..."),
]
# 想加一个安全检查步骤？想跳过某个阶段？都要改 Python 源码

痛点三：跨 Agent 数据传递靠字符串

旧 Chain 中上游输出全文作为 {previous} 注入下游 prompt。没有 Schema 约束——planner 输出可能是 Markdown、可能是 JSON、可能混在一起，writer 靠正则提取信息，脆弱且不可靠。

1架构总览：三层分离 + 文件布局

2.3 第一步：AST 解析 + meta 提取

parse_workflow_script 是整个引擎的入口。它做三件事：① 解析 meta 字面量、② 运行确定性安全检查、③ 把 body（meta 之后的脚本）提取出来。

parse_workflow_script — 核心流程
def parse_workflow_script(script: str) -> tuple[WorkflowMeta, str]:
    # 1. Python ast 模块解析整个脚本
    tree = ast.parse(script, mode="exec")

    # 2. 第一条语句必须是 meta = { name: '...', description: '...' }
    first = tree.body[0]
    # 检查：是 Assign 节点、目标是 Name(id='meta')、值是字面量
    if not isinstance(first, ast.Assign): raise ValueError(...)
    if first.targets[0].id != "meta": raise ValueError(...)

    # 3. 只接受纯字面量——不允许变量、函数调用、f-string
    meta_value = _evaluate_ast_node(first.value)
    # _evaluate_ast_node 递归处理 Constant、List、Dict、UnaryOp(-n)
    # 遇到任何非字面量节点直接抛 ValueError

    # 4. 验证 name 和 description 是非空字符串
    meta = _validate_meta(meta_value)

    # 5. ★ 对 body（meta 之后的所有语句）运行确定性检查
    for node in tree.body[1:]:
        _DeterminismVisitor().visit(node)

    # 6. 从 meta 结束行号切出 body 文本
    body = "\n".join(script.split("\n")[first.end_lineno:])

    return meta, body

2.3.1 _evaluate_ast_node —— 严格字面量求值

_evaluate_ast_node — 只接受纯数据
def _evaluate_ast_node(node: ast.AST) -> Any:
    match node:
        case ast.Constant(value=v) if isinstance(v, (str, int, float, bool)) | v is None:
            return v                                    # 基本类型
        case ast.Constant(value=v):
            raise ValueError(f"unsupported: {type(v)}")  # 拒绝 complex 等
        case ast.List(elts=elts):
            return [_evaluate_ast_node(e) for e in elts]   # 递归列表
        case ast.Dict(keys=keys, values=values):
            # 禁止 **dict 解包：keys 中不能有 None
            return {_evaluate_ast_node(k): _evaluate_ast_node(v)
                    for k, v in zip(keys, values)}
        case ast.UnaryOp(op=ast.USub(), operand=ast.Constant(value=(int()|float()) as v)):
            return -v                                   # 负数
        case _:
            raise ValueError(f"non-literal: {type(node)}")

2.3.2 _DeterminismVisitor —— 拒绝所有危险构造

_DeterminismVisitor — AST 级安全审计
class _DeterminismVisitor(ast.NodeVisitor):
    """遍历 AST，拒绝所有危险节点。"""

    def visit_Import(self, node: ast.Import):
        raise ValueError("import statements are not allowed")

    def visit_ImportFrom(self, node: ast.ImportFrom):
        raise ValueError("import statements are not allowed")

    def visit_Call(self, node: ast.Call):
        # 拒绝危险函数调用
        match node.func:
            case ast.Name(id=name) if name in (
                "open", "eval", "exec", "compile",
                "globals", "locals", "__import__",
            ):
                raise ValueError(f"{name}() not allowed")
            # 拒绝属性绕过：obj.__import__(), obj.__subclasses__() 等
            case ast.Attribute(attr=attr) if attr in (
                "__import__", "__subclasses__", "__class__",
            ):
                raise ValueError(f".{attr} not allowed")
        self.generic_visit(node)  # 继续递归检查子节点
为什么要在 AST 层就做安全检查？
因为 Python 的 exec() 执行的是字符串。如果不做 AST 检查，恶意脚本可以写 __import__('os').system('rm -rf /')，到运行时才发现就晚了。AST 检查在代码执行前就把它挡掉——检查先行，执行在后。

2.4 第二步：构建沙箱并执行

run_workflow 是真正的执行入口。它把 body 包装成 async def __workflow__():，注入受限 globals，然后在安全沙箱中执行。

run_workflow — 沙箱执行的核心
async def run_workflow(script, options=None) -> WorkflowRunResult:
    started = time.monotonic()

    # ── 1. 解析 ──
    meta, body = parse_workflow_script(script)

    # ── 2. 确定并发数 ──
    cpu_count = os.cpu_count() or 4
    default_concurrency = max(1, min(cpu_count - 2, 16))
    concurrency = max(1, min(options.concurrency or default_concurrency, 16))
    sem = asyncio.Semaphore(concurrency)

    # ── 3. 构建沙箱 globals（详细见 2.5 节）──
    sandbox_globals = {...}

    # ── 4. 包装执行 ──
    wrapper = ("async def __workflow__():\n"
               + "\n".join(f"  {line}" for line in body.split("\n")))
    local_vars = {}
    exec(wrapper, sandbox_globals, local_vars)
    result = await local_vars["__workflow__"]()

    # ── 5. 验证结果可序列化 ──
    _assert_serializable(result)

    # ── 6. 返回汇总 ──
    return WorkflowRunResult(
        meta=meta, result=result, logs=state["logs"],
        phases=state["phases"], agent_count=state["agent_count"],
        duration_ms=(time.monotonic() - started) * 1000,
    )

2.5 沙箱 globals 构建

这是工作流安全的最后防线——即使在 AST 检查通过后，运行时仍受限于严格受限的全局命名空间：

sandbox_globals — 脚本里能看到的全部全局变量
sandbox_globals = {
    # ★ 三大编排原语

    "cwd":      options.cwd,  # 工作目录
    "budget":   _Budget(),    # Token 预算追踪

    # ★ 安全别名（无文件 I/O、无 import）
    "JSON":     json_module,  # json.dumps / json.loads
    "Math":     math,         # math.sqrt 等
    "Array":    list,         # JS 友好的别名
    "Object":   dict,
    "Map":      dict,
    "Set":      set,

    # ★ 受限 builtins
    "__builtins__": _build_safe_builtins(log_fn),
    # 只有：str,int,float,bool,list,dict,set,tuple
    #       len,range,enumerate,zip,map,filter
    #       sorted,reversed,min,max,sum,any,all
    #       abs,chr,ord,isinstance,type,print(=log_fn)
    #       Exception,ValueError,TypeError,KeyError,IndexError

    #        globals, locals, getattr, setattr, delattr
    #        super, classmethod, staticmethod, property

2.6 执行方式：包装成 async def 然后用 exec()

核心技巧——将 body 文本包装成一个 async 函数，然后用 exec() 定义它，再 await 调用：

包装与执行
# body 是去掉了 meta = {...} 之后的脚本文本，例如：
#   phase('Analyze')
#   analysis = await agent('分析 diffs...', {'label': 'diff analysis'})
#   return {'result': analysis}

wrapper = "async def __workflow__():\n" + "\n".join(
    f"  {line}" for line in body.split("\n")
)
# 生成：
#   async def __workflow__():
#       phase('Analyze')
#       analysis = await agent(...)
#       return {'result': analysis}

local_vars = {}
exec(wrapper, sandbox_globals, local_vars)     # 定义函数
result = await local_vars["__workflow__"]()  # 执行它
exec() 为什么安全？
exec(code, globals, locals) 中，globals 指定了代码执行时的全局命名空间。我们把 __builtins__ 替换成了只有安全函数的白名单版本，所以代码里写 open('file.txt') 会报 NameError——因为在 globals 中根本不存在 open。

3三大编排原语：agent / parallel / pipeline

沙箱脚本中可用的三个核心函数，覆盖所有任务拓扑结构：串行 agent（单任务委托）、并行 fan-out（无依赖任务同时跑）、流水线 pipeline（每项串行、项间并发）。三者都受 asyncio.Semaphore 全局并发控制。

3.1 agent(prompt, opts) — 串行委托

_agent — 完整的子 Agent 调度流程 (workflow.py:412-481)
async def _agent(prompt, agent_opts=None):
    # ① 检查中止信号
    _check_aborted()
    # ② 检查 Token 预算
    if budget.remaining() <= 0: raise RuntimeError("budget exhausted")

    # ③ 标准化选项，确定 label、phase、schema
    norm_opts = _normalize_agent_options(agent_opts)

    # ④ ★ 如果 opts 中指定了 agent: "wiki-writer"
    #    从 args['agent_defs'] 中查出该 Agent 的工具白名单、系统提示词、skills
    if norm_opts.agent:
        agent_def = args['agent_defs'].get(norm_opts.agent)
        if agent_def:
            agent_active_tools = agent_def['tools']      # ['read','write','edit',...]
            agent_system_prompt = agent_def['system_prompt'] # Agent 角色的行为指导
            agent_skill_names = agent_def['skills']        # ['code-analysis']

    # ⑤ 内层 runner：计数器+1、触发回调、调用 WorkflowAgent.run()
    async def _agent_runner():
        state["agent_count"] += 1
        if options.on_agent_start: options.on_agent_start(...)

        try:
            result = await agent_runner.run(
                task_prompt,
                label=label, schema=norm_opts.schema,
                instructions=instructions, signal=signal,
                event_callback=options.on_event,
                active_tools=agent_active_tools,       # 工具白名单
                system_prompt=agent_system_prompt,     # 角色提示词
                skill_names=agent_skill_names,         # 技能名称列表
            )
            if options.on_agent_end: options.on_agent_end({"result": result})
            return result
        except Exception as e:
            # ★ 单个 agent 失败返回 None，不影响其他 agent
            if options.on_agent_end: options.on_agent_end({"error": str(e)})
            return None

    # ⑥ ★ 通过信号量控制并发
    async with sem:
        return await _agent_runner()
关键设计：agent 名称 → 配置查表
脚本中写 agent('prompt', {'agent': 'wiki-writer'})，引擎运行时从 args['agent_defs']['wiki-writer'] 查出 tools、system_prompt、skills——完全解耦。改 Agent 行为只需改 .md 文件，脚本不变。

3.2 parallel(thunks) — 并发 fan-out

_parallel — 所有 thunk 同时启动，失败不中断 (workflow.py:484-498)
async def _parallel(thunks: list):
    if not isinstance(thunks, list):
        raise TypeError("parallel() expects a list of functions")

    # ★ _safe_thunk：包装每个 thunk，失败返回 None 而不是抛异常
    async def _safe_thunk(thunk, index):
        try:
            return await thunk()
        except Exception as e:
            if signal and signal.is_set(): raise
            log(f"parallel[{index}] failed: {e}")
            return None

    # ★ asyncio.gather 并发执行，每个 thunk 内部通过 _agent 的 semaphore 排队
    return await asyncio.gather(
        *[_safe_thunk(t, i) for i, t in enumerate(thunks)]
    )

3.3 pipeline(items, *stages) — 流水线

_pipeline — 每项串行过阶段，项间并发 (workflow.py:501-523)
async def _pipeline(items: list, *stages):
    if not isinstance(items, list):
        raise TypeError("pipeline() expects a list as first arg")

    async def _run_item(item, index):
        value = item                         # 初始值是 item 本身
        for stage in stages:                  # 逐阶段执行
            try:
                result = stage(value, item, index)
                # stage 可以是同步或异步函数
                if asyncio.iscoroutine(result):
                    value = await result       # await 异步 stage
                else:
                    value = result             # 直接用同步结果
            except Exception as e:
                if signal and signal.is_set(): raise
                log(f"pipeline[{index}] failed: {e}")
                return None
        return value

    # ★ 所有 item 并发执行，但每个 item 内部是串行的
    return await asyncio.gather(
        *[_run_item(item, i) for i, item in enumerate(items)]
    )

4WorkflowAgent：子会话的完整生命周期

workflow_agent.py 中的 WorkflowAgent 类负责为每个 agent() 调用创建、执行、销毁一个隔离的子 AgentSession。它是连接引擎和 LLM 的桥梁——接收 prompt+配置，创建会话，注入工具和 skills，执行并提取结果。

4.1 run() 方法的完整流程

WorkflowAgent.run() — 子 Agent 的完整生命周期 (workflow_agent.py:39-258)
async def run(self, prompt, *, label=None, schema=None,
            instructions=None, signal=None, event_callback=None,
            active_tools=None, system_prompt=None, skill_names=None):
    # ── ① 构建完整 prompt ──
    parts = []
    if system_prompt: parts.append(system_prompt)    # Agent 角色定义
    if instructions: parts.append(instructions)     # "Workflow phase: Analyze"
    parts.append(f"Task: {prompt}")

    # ★ Schema 场景：追加结构化输出合约指令
    if schema:
        parts.extend([
            "Final output contract:",
            "- Your final action MUST be a structured_output tool call.",
            "- The structured_output arguments are the return value.",
        ])

    full_prompt = "\n\n".join(parts)

    # ── ② 按需加载 skills ──
    if skill_names:
        all_skills = load_skills()                   # 加载所有注册的 skill
        skill_map = {s.name: s for s in all_skills.skills}
        skills = [skill_map[name] for name in skill_names if name in skill_map]
        skill_text = format_skills_for_prompt(skills)
        full_prompt = skill_text + "\n\n" + full_prompt  # 前置注入

    # ── ③ 结构化输出工具 ──
    if schema:
        capture = StructuredOutputCapture()
        subagent_tools.append(create_structured_output_tool(schema, capture))

    # ── ④ 创建内存会话 ──
    session = AgentSession(
        cwd=self.cwd,
        model=self.model,
        session_manager=SessionManager.in_memory(self.cwd),  # ★ 临时目录
        extra_tools=subagent_tools,
        ...
    )

    # ── ⑤ 设置工具白名单 ──
    if active_tools:
        if capture:
            active_tools = list(active_tools) + ["structured_output"]
        session.set_active_tools_by_name(active_tools)

    # ── ⑥ 订阅事件 → 转发给进度回调 ──
    if event_callback:
        session._agent.subscribe(_forward_event)
        # _forward_event 将 message_update / tool_execution_start/end
        # 转换为统一的事件 dict 并通过 event_callback 传到上层

    # ── ⑦ 安装中止监视器 ──
    if signal:
        abort_task = asyncio.ensure_future(_watch_abort())
        # _watch_abort 轮询 signal，触发时调用 session.abort()

    # ── ⑧ 执行 ──
    await session.prompt(full_prompt)

    # ── ⑨ 提取结果 ──
    if schema and capture and capture.called:
        return capture.value                 # ★ 结构化输出：返回 dict
    return self._last_assistant_text(session)  # 普通输出：最后一条 assistant 文本

    # ── ⑩ 清理（finally 块）──
    finally:
        if abort_task: abort_task.cancel()
        session.dispose()   # ★ 清理临时目录，释放资源

4.2 事件转发机制

WorkflowAgent 订阅 AgentSession 的内部事件，将子 Agent 的工具调用和文本输出转发给 event_callback，最终流向 SSE：

事件转发 — 将子 Agent 内部行为暴露给上层
def _forward_event(event):
    evt = {}
    if event.type == "message_update":
        # 子 Agent 正在输出文本
        evt = {"text": event.assistant_message_event.delta}
    elif event.type == "tool_execution_start":
        # 子 Agent 开始调用工具
        evt = {"tool": event.tool_name, "args": str(event.args)[:120]}
    elif event.type == "tool_execution_end":
        # 子 Agent 工具调用完成
        evt = {"tool": event.tool_name, "is_error": event.is_error}
    evt["_subagent"] = label        # 标记是哪个 agent 的事件
    event_callback(evt)               # → WorkflowRunOptions.on_event → SSE

5结构化输出：从回调捕获到类型契约

子 Agent 默认返回文本。但下游阶段需要结构化的 dict——StructuredOutputCapture 是一个巧妙的"陷阱工具"：LLM 调用它时，捕获其参数作为返回值。使用者得到了类型安全的 dict，而不是需要解析的字符串。

5.1 工作原理

structured_output.py — 完整实现 (57行)
class StructuredOutputCapture:
    """可变容器——记录 structured_output 工具是否被调用，以及调用参数。"""
    def __init__(self):
        self.value: Any = None      # 调用参数（即结构化输出数据）
        self.called: bool = False   # 标记是否被调用过

def create_structured_output_tool(schema, capture, name="structured_output"):
    """创建工具：参数定义遵循 schema，执行时把参数存入 capture。"""

    async def _execute(tool_call_id, params, signal=None, on_update=None):
        capture.value = params      # ★ 保存参数
        capture.called = True       # ★ 标记已调用
        return AgentToolResult(
            content=[TextContent(type="text", text="Structured output received.")],
            details=params,
        )

    return AgentTool(
        name=name,
        label="Structured Output",
        description="Return the final machine-readable result.",
        parameters=schema,          # ★ JSON Schema 作为工具的参数定义
        execute=_execute,
    )
图 5-1　结构化输出的四步流程
为什么不直接用 LLM 的 tool_use 机制？
实际上就是在用——structured_output 就是一个普通的 AgentTool（有 name、description、parameters、execute）。LLM 看到这个工具就像看到任何其他工具一样，可以主动调用它。区别在于它的 execute 实现不是做业务操作，而是"捕获参数并标记"。这是一种优雅的借用——用现有的 tool-calling 基础设施实现了结构化输出，无需新增任何协议。

6YAML 编译器：声明式 → Python 脚本

compiler.py 是 workflow 的"用户界面"——它让用户用 69 行 YAML 替代 127 行 Python 脚本。编译器处理三件事：Schema 简写展开、变量插值解析、阶段代码生成（serial / parallel / pipeline）。

6.1 编译流程

compile_workflow_yaml — 从 YAML 到可执行 Python 的完整路径
def compile_workflow_yaml(yaml_text, agent_defs=None) -> str:
    # ① 解析 YAML
    doc = yaml.safe_load(yaml_text)
    name = doc["name"]
    description = doc["description"]
    phases = doc["phases"]
    variables = doc.get("variables")

    # ② 生成 meta = {...} 块
    lines.append("meta = {\n    'name': '{name}',\n    ...\n}")

    # ③ 编译 variables → Python 变量定义
    for vname, vprompt in variables.items():
        lines.append(f"_self_{vname} = {resolve_prompt(vprompt)}")

    # ④ 编译每个 phase —— 根据 mode 生成不同的 Python 代码
    phase_lines = compile_phases(phases, variables, ...)
    lines.extend(phase_lines)

    # ⑤ 生成 return 语句
    lines.append("return dict(_outputs)")

    return "\n".join(lines)

# step1 → step2 → ${previous} 指向前一步输出

                  {'label': 'diff analysis', 'agent': 'diff-analyzer'})

                  {'label': 'wiki planning', 'agent': 'wiki-planner',
                   'schema': {"type":"object", ...}})

# ── ② mode: parallel, for_each: [itemA, itemB] ──
# 所有 item 的 agent 同时启动

    results = await parallel([
      (lambda it=_item: agent(                    # ★ lambda 默认参数闭包绑定
          f'''页面: {it['wiki_page']}''',
          {'label': f'write-{it["wiki_page"]}', 'agent': 'wiki-writer'}
      )) for _item in plan['file_tasks']
    ])

# ── ③ mode: pipeline, for_each: [fileA, fileB] × [lint, review, fix] ──

    changed_files,
    lambda _prev, _orig, _idx: agent(f'对 {_orig} lint...', {'agent':'lint'}),
    lambda _prev, _orig, _idx: agent(f'{_prev}\n审查...', {'agent':'reviewer'}),
    lambda _prev, _orig, _idx: agent(f'{_prev}\n修复...', {'agent':'fixer'}),

编译器自动处理的安全措施
1. 空值保护：有 for_each 的阶段自动插入 if plan.get('file_tasks'): ... else: results = []。
2. lambda 闭包安全：lambda it=_item:（而非 lambda: agent(..., item)），用默认参数捕获当前值，避免 Python 闭包的延迟绑定陷阱。
3. 参数验证：编译器在生成脚本前校验 name/phases/agent 引用的有效性。

字段必填类型说明

description✅string描述这个工作流做什么

字段必填类型说明

for_each否string遍历表达式，如 ${outputs.Plan.file_tasks}。配合 mode 使用
steps✅list该阶段的步骤列表，至少一个 step

7.4 Step 字段说明

字段必填类型说明
agent✅stringAgent 定义名称，引用 builtin-agents/ 或项目 agents/ 中的 name 字段
label否string显示标签，用于日志和前端进度展示。支持 ${...} 变量
prompt✅string发送给 agent 的任务描述。支持全部 ${...} 变量插值语法
output_schema否dict结构化输出定义，使用 Schema 简写语法。有此项时 agent 必须调用 structured_output 工具

7.5 三种 Mode 详解

serial（默认）— 串行执行

Step 按书写顺序依次执行。每个 step 的 ${previous} 指向上一个 step 的输出。

适用：有严格先后依赖的步骤，如 先分析 → 再制定计划。

parallel — 并发执行

所有 step 同时启动，互不等待。有 for_each 时，将数组的每个元素展开为一个 step 实例，全部并发。

适用：独立任务批量处理，如 同时写 10 个 wiki 页面。

pipeline — 流水线

必须配合 for_each。每个 item 串行经过所有 step，但不同 item 之间并发。

适用：每个文件都要经过 lint→review→fix 三步，但文件间并发处理。

serial + for_each — 遍历串行

遍历数组，每个元素按 steps 串行执行，元素之间也是串行（一个处理完再处理下一个）。

适用：需要对每个元素执行多步操作且需要严格控制顺序时。

mode 与 for_each 组合速查

modefor_each行为典型场景
serial无steps 顺序执行，${previous} 指向前一步Analyze → Plan
parallel无所有 steps 同时启动同时查多个数据源
parallel有每个 item 对应一个 step，全部并发（fan-out）对 Plan 中每个 file_task 启动 writer
pipeline有item 内串行经过所有 step，item 间并发每个文件 lint → review → fix
serial有遍历 items，每个 item 串行执行所有 steps逐文件分析+修复（需严格顺序）

7.6 完整示例：Wiki 同步工作流

这是一个真实可运行的 wiki-sync workflow，演示了三种 mode 的组合使用：

.wiki/workflows/sync.yaml — 完整 wiki 同步
name: wiki_sync
description: 分析 VCS 提交并更新 wiki 页面
concurrency: 8                         ← 最多 8 个 writer 同时写

variables:                             ← 可选：顶层变量，减少重复
  task: |
    提交信息: ${commit_message}
    变更文件:
    ${join(changed_files, "- ${item}\n")}
    受影响的 Wiki 章节: ${affected_sections}
    Diff 目录: ${diffs_dir}

phases:
  # ─── Phase 1: serial 串行分析 ───
  - title: Analyze
    steps:
      - agent: diff-analyzer
        label: diff analysis
        prompt: |
          ${self.task}

          请逐一阅读 diff 目录下的文件，分析每个代码变更对 wiki 的影响。
          输出每个文件：变更了什么 → 影响哪个页面 → 怎么更新。

  # ─── Phase 2: serial 制定计划（结构化输出）───
  - title: Plan
    steps:
      - agent: wiki-planner
        label: wiki planning
        prompt: |
          基于分析结果，为每个文件生成具体的 wiki 更新指令：

          ${previous}                   ← 引用 Phase 1 的输出

          调用 structured_output 返回结果。
        output_schema:                 ← Schema 简写（会自动展开为 JSON Schema）
          file_tasks:
            file: str
            wiki_page: str
            section: str?              ← ? 表示可选字段
            action: {enum: [create, update, delete]}  ← 枚举约束
            instructions: str
          no_change_files: [str]       ← [str] → 字符串数组

  # ─── Phase 3: parallel fan-out 并行写 ───
  - title: Write
    mode: parallel                    ← ★ 并发模式
    for_each: ${outputs.Plan.file_tasks}  ← ★ 遍历 Plan 阶段结构化输出的数组
    steps:
      - agent: wiki-writer
        label: write-${item.wiki_page}   ← 每项的 label 不同
        prompt: |
          源文件: ${item.file}            ← 引用当前迭代元素的字段
          目标页面: ${item.wiki_page}
          操作: ${item.action}
          指令: ${item.instructions}

          请根据指令修改 wiki 页面，完成后说明修改内容。
编写 YAML 的三个关键点
  1. 变量优先级：item > self > outputs > previous > args。同名变量按此顺序解析。
  2. for_each 必须先有输出：${outputs.Plan.file_tasks} 能引用是因为 Plan 阶段在前面已经执行完毕。不能跨 phase 引用尚未执行的阶段。
  3. 空值安全由编译器自动处理：for_each 阶段编译后会自动生成 if items: ... else: results = [] 的空检查，YAML 中无需手写。

10三层沙箱安全设计

Workflow 脚本由用户编写甚至由 LLM 生成——必须假设它不可信。引擎在编译时（AST）、加载时（globals）、执行时（子会话）三个层面筑起防线。

🛡️ 第一层：AST 编译时

_DeterminismVisitor 遍历完整语法树，拒绝：

  • import / from ... import
  • open() / eval() / exec() / compile()
  • globals() / locals() / __import__()
  • .__subclasses__() / .__class__ 绕过

发生在 parse_workflow_script() 中，代码执行前就拦截。

🔒 第二层：运行时 globals

__builtins__ 被替换为白名单（只有 str/int/list/len/sorted 等纯函数），globals 中不存在：

  • open / __import__ / eval / exec
  • getattr / setattr / delattr
  • globals / locals
  • super / classmethod

即使 AST 漏了，exec() 时也调不到这些函数。

🧩 第三层：子 Agent 隔离

每个 agent() 调用创建独立的临时目录 AgentSession：

  • SessionManager.in_memory(cwd) 创建临时 session 目录
  • session.dispose() 清理所有临时文件
  • 子 agent 只能看到自己的 session 目录
  • 子 agent 之间不共享任何状态

即使一个子 agent 出了问题，不影响其他。

🧵 第四层：并发控制

asyncio.Semaphore 限制同时运行的 agent 数：

  • 默认 max(1, min(cpu_count-2, 16))
  • 每个 agent 通过 async with sem: 获取槽位
  • 防止 LLM API 被瞬间打爆
  • 可配置 concurrency 参数覆盖

12设计哲学与关键决策

决策 1：脚本用 Python 而非 JavaScript

TS 原版工作流脚本是 JS。移植时做了关键决断——改用 Python 语法（meta = {...} 替代 export const meta = {...}）。

理由：工作流脚本语法极简单（变量赋值、函数调用、await），JS 和 Python 在这个子集中几乎完全相同。用 Python 可以原生 exec()，无需嵌入 JS 解释器。模型生成 Python 和生成 JS 一样熟练。

决策 2：平行端点而非替换

Workflow 端点 /workflow-sync/ 与旧 Chain 端点 /chain-sync/ 在同一 router 中共存。

理由：零破坏。前端通过 syncMode 切换。旧用户不受影响，新功能渐进推广。

决策 3：编译器而非解释器

YAML 被编译成 Python 脚本再执行——不是在运行时逐条解释 YAML。

理由：YAML 编译成 Python 后，走和手写 Python 完全相同的执行路径（沙箱+原语）。不需要两套执行器，且生成的 Python 脚本可被审查和调试。

决策 4：优雅降级 > 全局失败

单个 agent 失败返回 None，不抛异常中断整个 workflow。

理由：workflow 本质上是一个批处理任务（一个 commit 改 N 个文件）。一个文件的 wiki 写失败，不应该阻止其他 9 个文件的成功更新。调用方决定如何处理 None。

决策 5：两套 Agent 定义完全隔离

Chain 的 agents/*.md 和 Workflow 的 builtin-agents/*.md 完全独立。

理由：虽然格式相同，但两者的上下文和职责不同。Workflow 的 diff-analyzer 需要处理 per-file diff，Chain 的需要处理整体 diff——它们提示词有差异。隔离避免耦合。

决策 6：从 TypeScript 到 Python 的 1:1 移植

核心数据结构、原语语义、沙箱概念——完全从 pi-dynamic-workflows TS 项目移植。

映射：acorn → ast / vm → exec() / createLimiter → Semaphore / terminate:true 工具 → StructuredOutputCapture / SessionManager.inMemory() → in_memory()
