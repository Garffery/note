pi-wiki-agent 面试复习笔记

一句话：这是一个 VCS 驱动的 Wiki 文档同步 Agent 平台，能够监听代码提交，根据 diff 自动分析受影响文档，规划 Wiki 更新任务，并通过多 Agent 工作流自动修改文档。

LLM Agent 多 Agent 编排 DAG 并行执行 YAML 工作流编译器 结构化输出 断点续跑 FastAPI + Vue 3 SSE 流式进度 LLM-as-Judge
业务问题代码变化后 Wiki 文档容易过期，人工维护成本高。
核心方案把 diff 作为输入，把 Wiki 作为可追溯的派生产物。
面试重点讲清 Agent 工程化，而不是只讲 Prompt。

1. 项目定位

这个项目不是普通聊天机器人，而是一个面向真实代码仓库的 Agent 应用系统。它解决的问题是：项目代码频繁变化，但 Wiki 文档不会自动同步，长期会出现过期内容、断链、缺失章节和代码文档不一致。

你的设计思路是：把 Wiki 当作代码仓库的派生产物。每次提交产生 diff，系统通过反向索引找到受影响的 Wiki 章节，再由 Agent 完成影响分析、更新规划和文档写入。

面试时的定位话术： 我做的是一个 VCS 驱动的文档同步 Agent 平台。它不是让 LLM 自由写文档，而是把代码 diff、反向索引、结构化规划、DAG 执行、断点恢复和质量评测串成一个可运行的工程系统。

2. 面试讲述主线

  1. 先讲痛点：代码变更后 Wiki 很容易腐烂，靠人补文档不稳定。
  2. 再讲输入输出：输入是 commit message、changed files、unified diff；输出是被精确更新的 `.wiki/*.md` 页面。
  3. 讲核心链路：Analyze 分析影响，Plan 生成结构化任务，Write 并行更新页面。
  4. 讲工程化：反向索引、章节锚点、结构化输出、DAG 并发、checkpoint、沙箱、评测框架。
  5. 讲结果价值：减少重复 LLM 调用，提升文档更新稳定性，可视化 Agent 执行过程，能被测试和评估。
注意：不要把重点放在“我调用了某个大模型”。重点应该放在“我如何让 LLM 在复杂任务里稳定、可控、可恢复、可评测地工作”。

4. 核心执行链路

一次提交同步发生了什么

  1. 用户选择项目和提交，系统从 VCS 获取变更文件、commit message、revision 和 diff。
  2. WikiIndexer 根据 changed files 查询反向索引，得到受影响的 Wiki 页面和章节。
  3. 系统把每个变更文件的 diff 写入 `.wiki/chain/diffs/<revision>/`，让后续 Agent 可以按文件读取。
  4. 加载内置或项目自定义 Agent 定义，例如 diff-analyzer、wiki-planner、wiki-writer。
  5. 加载 `.wiki/workflows/sync.yaml`，经 YAML → IR → AST → Python 编译为可执行工作流。
  6. 运行工作流：Analyze 分析 diff 影响，Plan 生成结构化任务，Write 按 DAG 并行更新 Wiki 页面。
  7. 执行过程中通过 SSE 把 phase、Agent 开始结束、工具调用、文本增量推给前端。
  8. 成功后清理临时 diff 和 checkpoint；如果失败，则保留 checkpoint 用于恢复。

5. 模块拆解

1. 反向索引与 Wiki 格式

Wiki 页面使用 WIKI_SECTION HTML 注释作为稳定锚点，用 **source**:[...](file://...) 建立 Wiki → 代码追溯，再用 repowiki-metadata.json 建立代码 → Wiki 的反向索引。

价值：让 Agent 精确知道改哪个页面、哪个章节，而不是在长 Markdown 中猜位置。

2. 工作流编译器

用户用 YAML 描述 phase、step、Agent、输出 schema 和执行模式。系统先解析成 IR 数据结构，再用 WorkflowASTBuilder 生成 Python AST，最后 ast.unparse 成脚本交给运行时。

价值：工作流可配置，但执行逻辑仍然可控、可检查、可注入 checkpoint。

3. 运行时沙箱

run_workflow() 会解析脚本并检查危险 AST 节点，拒绝 import、open、eval、exec、globals 等能力，只注入安全 builtins 和 Agent 调用函数。

价值：项目工作流可能来自用户仓库，不能直接执行不受限制的 Python。

4. WorkflowAgent 子 Agent

每次 agent() 调用都会创建一个独立的 WikiSession。如果 step 声明 schema，会挂载 structured_output 工具，要求模型最终通过工具调用返回结构化结果。

价值：每个子 Agent 有独立上下文、工具白名单和系统提示词，职责更清晰。

5. DAG 并行与断点续跑

工作流支持 serial、parallel、dag、pipeline。DAG 模式下根据任务依赖做拓扑执行，并为 phase 或每个 task 生成 checkpoint 文件。

价值：大型 Wiki 同步失败后不用重跑全部 LLM 调用，只恢复失败任务。

6. 桌面端与可观测性

FastAPI 暴露 REST 和 SSE 接口，Vue 3 前端实时展示 phase、Agent、工具调用、生成文本、模型设置和质量检查结果。

价值：Agent 不再是黑盒脚本，用户能看到它正在做什么。

7. 技术细节复习

为什么需要反向索引

如果只把完整 diff 丢给 LLM，它需要自己判断哪些 Wiki 页面受影响，成本高且容易漏。反向索引把源文件映射到 Wiki 页面和章节，系统可以先用确定性逻辑缩小范围，再交给 Agent 做语义判断。

为什么用 WIKI_SECTION 注释

Markdown 标题会被模型改写，行号也会随内容变化而失效。HTML 注释对读者不可见，但对 Agent 和解析器稳定可见，适合作为章节边界。

为什么 Plan 阶段要结构化输出

Plan 阶段是后续执行的接口。如果它输出自然语言，Writer 阶段难以稳定解析，也无法做并行调度。结构化输出让任务包含 wiki_page、section、action、instructions 等字段，系统可以校验、调度和记录。

为什么用 AST 而不是字符串拼接 Python

AST 可以在生成代码前做结构化校验，避免字符串模板带来的语法错误和注入风险。并且 checkpoint、并发控制、日志、沙箱约束可以统一由编译器插入，而不需要每个工作流手写。

为什么要断点续跑

LLM 调用成本高、耗时长，也可能因为网络、限流或模型输出错误失败。断点续跑把每个阶段或任务变成可恢复单元，失败后只重跑未完成部分。

为什么要 SSE

Agent 执行时间长，而且中间会调用工具、并行运行多个子任务。SSE 适合服务端单向持续推送，让前端实时显示进度，不需要轮询。

为什么要 LLM-as-Judge

Wiki 文档质量不是简单字符串匹配能判断的。结构断言可以检查页面和章节是否被改，但事实正确性和覆盖完整性需要语义评估，所以引入 LLM Judge，并用结构化输出约束评分结果。

8. 高频面试问题与回答要点

Q1：这个项目和普通 RAG / 聊天机器人有什么区别？
普通聊天机器人主要解决问答，这个项目解决的是代码仓库里的持续文档维护。它不是只把上下文喂给模型，而是把 VCS、反向索引、工作流编排、工具调用、结构化输出、断点恢复和质量评测组合起来，让 Agent 能执行一个可落地的工程任务。
Q2：为什么要拆成 Analyze、Plan、Write 三个阶段？
因为直接让一个 Agent 从 diff 到修改文档，任务太大且不可控。Analyze 专注理解代码影响，Plan 专注把影响转成结构化任务，Write 专注执行具体页面修改。这样每个 Agent 职责单一，输出更容易校验，也方便并行和失败恢复。
Q3：DAG 并行解决了什么问题？
不同 Wiki 页面或章节通常可以独立更新，但有些任务之间存在依赖。DAG 允许没有依赖的任务并行执行，有依赖的任务按拓扑顺序执行。这样既能提升速度，又避免多个 Writer 同时修改互相关联内容导致冲突。
Q4：LLM 输出不稳定怎么办？
关键规划阶段不解析自由文本，而是使用 structured_output 工具强制模型按照 JSON Schema 返回结果。系统拿到结构化数据后可以做字段校验、枚举约束和任务调度。对于最终文档内容，则通过章节边界、source 链接和质量检查降低风险。
Q5：为什么要做 YAML → AST 编译器？
YAML 对用户友好，适合描述工作流；Python AST 对系统友好，适合插入并发、checkpoint、日志、结构化输出和安全限制。相比字符串拼接，AST 更可控，也能在执行前做静态检查。
Q6：运行用户自定义工作流有没有安全风险？
有，所以运行时做了沙箱约束。脚本执行前会遍历 AST，拒绝 import、open、eval、exec、globals 等危险操作。运行时只注入有限 builtins 和受控的 agent、checkpoint、log 等函数。
Q7：断点续跑具体怎么设计？
以 revision 作为 namespace，在 `.wiki/checkpoints/<revision>/` 下保存 phase 或 task 的结果。执行前先 load checkpoint，命中则跳过对应 LLM 调用；未命中则正常执行并 save。DAG for_each 模式下可以细到单个任务，例如 50 个任务完成 47 个后失败，下次只跑剩下 3 个。
Q8：怎么判断哪些 Wiki 页面需要更新？
系统维护 `.wiki/repowiki-metadata.json` 反向索引，记录 source file、wiki page、section id 的映射。提交发生后，根据 changed files 查索引，得到 affected sections，再把这些信息交给 Analyze 和 Plan 阶段。
Q9：为什么不让 Agent 自己全仓库搜索？
全仓库搜索成本高、慢、不稳定，而且容易引入无关上下文。确定性索引可以先把范围缩小到相关章节，Agent 只处理必要上下文，速度和准确性都会更好。
Q10：如果多个 Writer 同时改同一个 Wiki 页面怎么办？
Plan 阶段会尽量把同一页面的多个文件修改合并成一条任务；对于存在依赖关系的任务，可以通过 DAG 依赖控制执行顺序。后续还可以引入页面级锁或合并策略来增强并发写安全。
Q11：质量检查器检查什么？
主要分为可追溯性和新鲜度。可追溯性包括 source 链接是否存在、反向索引是否指向有效页面和源文件、是否有孤儿页面、索引章节是否已删除。新鲜度包括源文件是否比 Wiki 更新、空章节、重复章节、HTML 实体残留等。
Q12：怎么评估 Agent 写得好不好？
测试用例由 diff.txt、args.json、expected.json 组成。结构断言检查是否更新了预期页面和章节；多次运行计算 pass@k；LLM-as-Judge 从 correctness 和 completeness 两个维度评价内容是否准确、是否覆盖关键变更。
Q13：为什么需要桌面端？
Agent 工作流执行时间长，用户需要看到进度、工具调用、错误和结果。桌面端把命令行能力产品化，提供项目管理、同步触发、SSE 流式进度、质量面板、模型管理和定时任务配置。
Q14：这个项目有哪些难点？
难点不在调用 LLM，而在把 LLM 放进可靠系统里：任务如何拆分、输出如何约束、并发如何调度、失败如何恢复、上下文如何缩小、结果如何评估、用户如何观察执行过程。
Q15：如果让你继续优化，你会做什么？
可以从四个方向讲：一是把 JSON 反向索引升级为 SQLite 或 FTS，提高大仓库查询能力；二是增加页面级锁和冲突合并；三是引入更细粒度的成本和 token 监控；四是完善人工反馈闭环，把用户修正文档的行为反哺评测和提示词。

9. 代码级追问与答案

这一章用于应对面试官从“架构问题”继续追到“代码怎么实现”。回答时建议先说链路，再点出关键文件和函数，最后补一句设计取舍。

Q1：FastAPI 请求进来后，workflow-sync 的完整调用链是什么？

代码入口desktop/src/pi_wiki_desktop/api/v1/endpoints/workflow_sync.py 的 workflow_sync_commit_stream()。

请求进入后，接口先通过 load_projects() 找项目配置，再用 create_monitor(cfg["path"]) 获取 VCS monitor，通过 monitor.get_commit(rev) 取提交信息。然后加载 sync.yaml，创建 asyncio.Queue 承接 Agent 进度事件，定义 on_agent_start、on_agent_end、on_phase、on_event 这些回调。真正执行逻辑被包进内部协程 _run_workflow()，再交给 run_background("workflow-sync", _run_workflow()) 后台执行。

面试回答：“入口是 FastAPI 的 async endpoint，它在 uvicorn 的事件循环里运行。endpoint 不直接阻塞等待 Agent 完成，而是创建后台 task，同时通过 SSE 持续把 queue 里的进度事件返回给前端。”

Q2：run_background() 里的 asyncio.create_task 做了什么？

代码入口desktop/src/pi_wiki_desktop/activity.py 的 run_background(label, coro)。

asyncio.create_task(coro) 会把 coroutine 包装成 Task，注册到当前正在运行的事件循环中，并安排它后续执行。因为调用链来自 FastAPI 的 async def endpoint，所以此时已经处于 uvicorn / Starlette 管理的 asyncio event loop 里。

项目里还会把 id(task) 记录到 _active 字典，用于桌面宠物或活动状态判断；task.add_done_callback(lambda t: _active.pop(id(t), None)) 表示任务完成、异常或取消时自动清理活跃状态。

注意点：如果在普通同步函数、且当前线程没有 running loop，直接调用 asyncio.create_task 会报 RuntimeError: no running event loop。

Q3：SSE 流式进度是怎么实现的？

代码入口workflow_sync.py 中的 queue: asyncio.Queue[dict] = asyncio.Queue()、_event_stream() 和 StreamingResponse。

后台任务执行 Agent 工作流，进度回调通过 queue.put_nowait({...}) 写入事件。HTTP 响应这边的 _event_stream() 是一个 async generator，它循环 await asyncio.wait_for(queue.get(), timeout=300)，拿到事件后 yield 成 SSE 格式：data: {...}\n\n。

当事件类型是 workflow_done 时，流式响应会 await task，确认后台任务收尾完成，然后 return 结束连接。

面试回答：“SSE 这块本质是生产者消费者模型。后台 Agent 是生产者，把事件写入 asyncio.Queue；StreamingResponse 是消费者，把事件按 SSE 协议推给浏览器。”

Q4：execute_workflow_sync() 具体负责什么？

代码入口packages/wiki-agent/src/pi_wiki_agent/core/workflow_sync.py 的 execute_workflow_sync()。

它是“提交同步”到“工作流运行”的桥接层。主要步骤是：校验 changed files；用 WikiIndexer(project_path).get_affected_sections(changed_files) 查询受影响 Wiki 章节；创建 .wiki/chain/diffs/<revision>/ 并写入每个文件的 diff；加载内置和项目自定义 Agent 定义；组装传给工作流的 args；将 YAML 工作流通过 compile_workflow_yaml(script, agent_defs) 编译成 Python 脚本；创建或复用 WorkflowAgent；最后调用 run_workflow()。

面试回答：“这个函数不是具体写 Wiki 的地方，它负责准备上下文和运行环境，把 VCS 信息、反向索引、diff 文件、Agent 定义、模型和回调都接到 workflow engine 上。”

Q5：工作流 YAML 是怎么变成可执行逻辑的？

代码入口packages/wiki-agent/src/pi_wiki_agent/core/workflow/ast_compiler/builder.py 的 WorkflowASTBuilder。

链路是 YAML → IR → AST → Python。YAML 先解析成 WorkflowDef、PhaseDef、StepDef 这样的 IR 数据结构。WorkflowASTBuilder.build() 再按固定结构生成一个 ast.Module，包括 meta、初始化变量、checkpoint 元数据、各个 phase、清理逻辑和 return。

不同执行模式走不同构建函数：_build_serial()、_build_parallel()、_build_dag()、_build_pipeline()。这样 checkpoint、并发、日志、结构化输出等逻辑可以统一由编译器注入。

面试回答：“我没有直接字符串拼接 Python，而是生成 AST。这样更容易做静态检查，也更容易统一插入 checkpoint 和并发控制。”

Q6：run_workflow() 如何保证用户工作流相对安全？

代码入口packages/wiki-agent/src/pi_wiki_agent/core/workflow/workflow.py 的 parse_workflow_script()、_DeterminismVisitor 和 run_workflow()。

执行前会先解析 Python AST，要求第一条语句是 literal 形式的 meta。随后 _DeterminismVisitor 遍历 AST，拒绝 import、open()、eval()、exec()、compile()、globals()、locals()、__import__ 等危险能力。

运行时不是给完整 Python 环境，而是构建受限 __builtins__，再注入受控的 agent、checkpoint、phase、log 等函数。

边界：这属于应用级沙箱，能拦住大部分明显危险操作，但如果要跑不可信第三方脚本，生产上还应该配合进程级隔离、容器或权限隔离。

Q7：结构化输出工具是怎么工作的？

代码入口packages/wiki-agent/src/pi_wiki_agent/core/workflow/structured_output.py 的 create_structured_output_tool()，以及 workflow_agent.py 的 WorkflowAgent.run()。

当 step 声明 schema 时，WorkflowAgent.run() 会创建 StructuredOutputCapture，并把 create_structured_output_tool(schema, capture) 追加到子 Agent 的工具列表中。这个工具的 parameters 就是 JSON Schema。

模型调用 structured_output 时，工具执行函数把参数保存到 capture.value，并设置 capture.called = True。子 Agent 结束后，WorkflowAgent.run() 如果发现 capture 被调用，就直接返回 capture.value，而不是解析自然语言。

面试回答：“Plan 阶段的输出不是靠正则解析，而是把 JSON Schema 暴露成一个 terminating tool，让模型通过工具调用交付机器可读结果。”

Q8：子 Agent 是如何隔离和恢复的？

代码入口packages/wiki-agent/src/pi_wiki_agent/core/workflow/workflow_agent.py 的 WorkflowAgent.run()。

每次运行子 Agent 都会创建一个 WikiSession。如果有 resume_from 且文件存在，就通过 SessionManager.open(resume_from) 恢复已有会话；否则用 SessionManager.in_memory(self.cwd) 创建新会话，并记录 last_session_path。

每个子 Agent 可以有自己的 label、system prompt、active tools、skills 和 schema。事件回调会把文本增量、工具开始和工具结束等事件转发给上层 SSE。

面试回答：“工作流里的 agent 调用不是复用一个大上下文硬塞所有任务，而是每个子任务创建独立会话。这样职责清晰，也方便从 session_path 恢复。”

Q9：checkpoint 断点续跑在代码里怎么落地？

代码入口packages/wiki-agent/src/pi_wiki_agent/core/workflow/checkpoint.py 的 CheckpointStore，以及 builder.py 中 _build_serial()、_build_dag()、_build_dag_*_branch()。

run_workflow() 会注入 CheckpointStore，namespace 通常和 revision 绑定。AST builder 生成的代码会在每个 phase 执行前调用 checkpoint.load()，命中则跳过执行；未命中则运行 Agent，并在成功后 checkpoint.save()。

DAG + for_each 更细：每个任务有独立 checkpoint。代码生成里区分 cached branch、resume branch、fresh branch：已完成的直接用 value；有 session_path 但没有 value 的尝试恢复；完全没有记录的正常执行。

面试回答：“断点不是业务函数里到处手写的，而是编译器生成的统一逻辑，所以所有执行模式都天然支持恢复。”

Q10：DAG 并行具体由谁负责？

代码入口builder.py 的 _build_dag()、_build_dag_for_each_body()。

YAML 中 phase 设置 mode: dag 后，编译器会生成 DAG 执行代码。任务 ID 和依赖来自 Planner 产出的任务字段或 step 配置。运行逻辑会根据依赖关系判断可执行任务，并配合并发限制执行多个 Agent。

这个设计把“任务依赖声明”和“执行调度实现”分开：LLM 或 YAML 只负责声明任务与依赖，调度、恢复、并发控制由引擎负责。

面试回答：“DAG 不是让模型自己并行，而是模型输出任务结构，系统用确定性调度执行。这样可控性比让 Agent 自己决定下一步更强。”

Q11：质量检查器的实现思路是什么？

代码入口packages/wiki-agent/src/pi_wiki_agent/core/wiki_quality.py 的 WikiQualityChecker.run_checks()。

它先遍历 `.wiki/**/*.md` 页面，再读取 repowiki-metadata.json。P0 类检查关注可追溯性，例如 source 链接是否指向存在文件、索引里的页面和源文件是否存在、是否有 orphan page、索引章节是否已删除。P1 类检查关注新鲜度和格式，例如源文件修改时间是否晚于 Wiki、空章节、重复章节、HTML entity 残留、frontmatter related 格式。

面试回答：“质量检查器是 Agent 输出后的治理层。它不依赖 LLM，先用确定性规则发现结构性问题，再把报告交给修复工作流。”

Q12：评测框架需要掌握到什么程度？

代码入口packages/wiki-agent/src/pi_wiki_agent/eval/runner.py 的 TestRunner。

你要能讲清 case 由 diff.txt、args.json、expected.json 组成。TestRunner.run_all() 遍历用例，_run_one() 负责重置 Wiki、执行 workflow、做结构断言，并在真实运行时调用 LLM Judge 评估内容正确性和完整性。

面试回答：“我没有只靠人工看效果，而是把真实提交 diff 抽象成测试用例。结构断言负责确定性检查，LLM Judge 负责语义质量评估，重复运行可以算 pass@k。”

11. 面试追问库与参考答案

这一章模拟面试官沿着 workflow_sync_commit_stream → execute_workflow_sync → run_workflow → dag/agent 这条链路逐层追问。回答时建议采用“三段式”：先给结论，再说代码入口，最后讲设计取舍或风险。

高频核心： 三阶段 Agent、YAML → AST → sandbox、DAG 拓扑调度、checkpoint 断点恢复、SSE + background task + queue，这五块最容易被深挖。

一、整体链路

Q1：你能从一次前端点击“同步”开始，完整讲一下请求到 Agent 执行结束的链路吗？
前端请求 /api/projects/{name}/workflow-sync/{rev}/stream，FastAPI 读取项目配置和 commit，加载 workflow YAML，创建 asyncio.Queue 和 SSE 回调，然后用 run_background() 启动后台任务。后台进入 execute_workflow_sync() 准备 diff、索引、Agent 定义并编译 YAML，最后由 run_workflow() 执行 Analyze / Plan / Write，多 Agent 进度通过 queue 推给 SSE。
Q2：workflow_sync_commit_stream() 为什么不直接 await execute_workflow_sync()，而是用 run_background()？
因为 workflow 是长耗时任务，如果直接 await，接口虽然也能等结果，但无法优雅地边执行边推送进度。后台 task 负责运行 Agent，SSE generator 负责持续读取 queue 并返回事件，两者解耦后前端能实时看到阶段、工具调用和最终状态。
Q3：这个接口为什么选择 SSE，而不是 WebSocket 或普通轮询？
这里是服务端单向推送：后端不断把 Agent 进度发给前端，前端不需要持续双向通信。SSE 比 WebSocket 简单，天然基于 HTTP，适合日志和进度流；轮询会增加延迟和请求开销，也不适合 token 流式输出。
Q4：如果前端断开 SSE 连接，后台 workflow 还会继续跑吗？
按当前结构，后台任务已经通过 asyncio.create_task() 加入事件循环，通常会继续运行。SSE 断开只影响事件消费端，不会自动取消后台 task。要实现断开即取消，需要在 StreamingResponse 或 request disconnect 检测里显式设置取消信号。
Q5：workflow_done 事件什么时候发？如果中间异常了，前端会收到什么？
_run_workflow() 成功执行完 execute_workflow_sync() 后会 put 一个 success: true 的 workflow_done。如果异常，会记录失败状态并 put success: false 和 error 字段，SSE 读到 workflow_done 后 await task 并结束连接。

二、FastAPI / asyncio

Q6：asyncio.create_task() 在这里创建的 task 属于哪个事件循环？
属于当前 FastAPI 请求所在的 running event loop，也就是 uvicorn / Starlette 管理的 asyncio 事件循环。因为 endpoint 是 async def，调用 run_background() 时已经在事件循环上下文里。
Q7：如果这个接口从 def endpoint 里调用 create_task() 会怎样？
普通 def endpoint 通常在线程池里执行，当前线程不一定有 running event loop，直接 asyncio.create_task() 可能抛 RuntimeError: no running event loop。所以这类后台异步任务适合从 async def endpoint 调用。
Q8：asyncio.Queue 在这里起什么作用？为什么不直接在回调里 yield？
Queue 是后台任务和 SSE generator 之间的异步桥梁。Agent 回调是由 workflow 执行过程触发的，不能直接控制 HTTP 响应的 yield；通过 queue，生产者只管 put 事件，消费者只管按 SSE 协议 yield。
Q9：_event_stream() 里面为什么要 await task？
收到 workflow_done 后说明后台逻辑已经放出了最终事件，但 await task 可以确保后台协程真正收尾完成。如果后台 task 有未传播的异常，这里也能让异常进入 await 流程，避免静默悬挂。
Q10：如果后台任务永远不往 queue 里写数据，SSE 会怎样？
_event_stream() 使用 asyncio.wait_for(queue.get(), timeout=300)。如果超时没有事件，会发送一个 {"type": "timeout"}，然后结束连接，避免 HTTP 连接无限挂住。

三、execute_workflow_sync

Q11：execute_workflow_sync() 的职责边界是什么？它和 run_workflow() 分别负责什么？
execute_workflow_sync() 是同步编排器，负责准备上下文：changed files、affected sections、diff 文件、agent_defs、模型、并发和 trace/replay。run_workflow() 是运行时内核，负责执行已经编译好的 workflow 脚本，注入 agent/dag/checkpoint 等运行时 API。
Q12：为什么一开始要用 WikiIndexer.get_affected_sections(changed_files)？
这是用确定性索引先缩小上下文范围。changed files 可以映射到具体 Wiki 页面和章节，Agent 不必全仓库猜哪些文档相关，能降低 token 成本、减少误改和漏改。
Q13：如果没有反向索引，能不能直接把完整 diff 丢给 Agent？缺点是什么？
可以做 demo，但生产效果差。完整 diff 会带来高 token 成本、相关页面定位不稳定、长上下文遗漏、误改无关章节等问题。反向索引把“查找范围”交给确定性代码，把“语义判断”交给 Agent。
Q14：为什么要把每个文件的 diff 写到 .wiki/chain/diffs/{revision}？
这样每个子 Agent 可以按需读取具体文件 diff，而不是所有上下文都塞进 prompt。它也让调试和复现更容易：某个 revision 的输入被落盘，Agent 可以通过工具读取。
Q15：_load_workflow_agent_defs() 加载内置 Agent 和项目自定义 Agent 时，谁的优先级更高？为什么？
内置 Agent 先加载，项目目录 .wiki/workflows/agents/*.md 后加载并覆盖同名定义。这样系统有默认能力，同时允许项目按自己的仓库规范定制 prompt、工具和模型。

四、WorkflowAgent / WikiSession

Q16：WorkflowAgent 和 WikiSession 的关系是什么？
WorkflowAgent 是工作流里的子 Agent runner，负责根据每个 step 创建并运行子任务；WikiSession 是具体 Agent 会话，里面包含模型、工具、system prompt、消息历史和事件流。
Q17：为什么每次子 Agent 调用都新建一个 WikiSession？
这样每个子任务上下文隔离，角色提示词、工具白名单、结构化输出工具和 session_path 都能独立管理。它也方便断点恢复：失败时可以根据某个子 Agent 的 session 文件继续。
Q18：WorkflowAgent.run() 中 full_prompt、system_prompt、instructions 分别承载什么？
system_prompt 是角色级长期约束，来自 agent definition；instructions 是 workflow runtime 根据 phase/schema 生成的额外执行要求；full_prompt 是本次任务消息，包含 label、任务内容和结构化输出约束。
Q19：skill prompt 可能重复，具体是哪两条路径导致的？
一条是在 WorkflowAgent.run() 根据 skill_names 把 format_skills_for_prompt() 拼进 full_prompt；另一条是在 WikiSession.__init__() 把 skills 拼进 system prompt。如果两边包含同一批 skill，就会重复出现 available_skills 说明。
Q20：structured_output 工具为什么作为 extra tool 注入，而不是让模型直接输出 JSON 文本？
工具调用有 schema 约束和明确的调用边界，参数由工具系统校验并捕获。直接输出 JSON 文本容易出现 markdown 包裹、格式错误、字段缺失或解释性文字混入，后续调度会不稳定。

五、run_workflow 运行时

Q21：为什么说 run_workflow() 像一个“小型工作流虚拟机”？
它解析 workflow body，创建运行状态，注入 agent/parallel/pipeline/dag/checkpoint/log/phase 等运行时 API，再在受限 globals 中执行 __workflow__()。workflow 脚本实际运行在它提供的运行时环境里。
Q22：parse_workflow_script() 为什么要求第一句必须是 meta = {...}？
meta 是工作流的声明信息，包括名称、描述和 phases。强制放在第一句可以先静态解析工作流元信息，便于 UI 展示、校验和结果返回，也避免执行 body 后才知道工作流是什么。
Q23：run_workflow() 注入了哪些运行时 API？各自干什么？
核心 API 包括：agent 调子 Agent，parallel 并发执行函数列表，pipeline 让数据经过多阶段处理，dag 按依赖拓扑执行任务，checkpoint 做断点保存/恢复，phase/log 做可观测性，args/cwd/budget 提供上下文。
Q24：sandbox_globals 里为什么要限制 __builtins__？
workflow 可能来自项目目录，不能给它完整 Python 权限。限制 builtins 可以减少文件访问、动态执行、导入和反射等风险，只暴露工作流真正需要的安全能力。
Q25：_DeterminismVisitor 禁止了哪些操作？这能完全保证安全吗？
它会拒绝 import、open、eval、exec、compile、globals、locals、__import__ 等危险操作。它是应用级防护，不等于强安全沙箱；对不可信代码，仍建议进程、容器或系统权限隔离。

六、DAG 调度

Q26：dag() 的输入数据结构是什么？
输入是 task dict 列表，每个 task 至少包含 id、fn、depends_on。id 是唯一任务标识，fn 是可 await 的任务函数，depends_on 表示前置依赖列表。
Q27：为什么要先校验 task 的 id、fn、depends_on？
DAG 调度依赖结构正确性。id 不唯一会覆盖结果，fn 不可调用无法执行，depends_on 类型错误会导致拓扑计算不可靠。提前失败比执行到一半才报错更好定位。
Q28：三色 DFS 环检测是怎么工作的？
每个节点有 WHITE、GRAY、BLACK 三种状态。DFS 进入节点标 GRAY，退出标 BLACK；如果遍历依赖时遇到 GRAY 节点，说明回到了当前递归栈中的节点，也就是存在环。
Q29：Kahn 算法在这里是怎么体现的？
代码先计算每个任务的 in_degree，即剩余依赖数。入度为 0 的任务进入 ready 队列并并发执行；任务完成后降低后继节点入度，新的 0 入度节点进入下一批 ready。
Q30：ready 队列代表什么？
ready 代表当前所有依赖都已满足、可以立即运行的任务集合。每一轮 ready 可以用 asyncio.gather 并发执行，从而最大化利用并发。
Q31：如果某个任务失败了，它的后继任务怎么处理？
失败任务会加入 failed 集合。后继任务执行前会检查依赖是否失败，如果依赖失败则跳过当前任务并返回 None，避免基于不完整结果继续生成错误内容。
Q32：seed 参数是干什么的？它和 checkpoint 怎么配合？
seed 表示已经完成的任务结果。DAG 开始时会把 seed 中非 None 的结果写入 results，并降低其后继任务入度。checkpoint 恢复时可以把已完成 task 作为 seed 注入，避免重复跑 LLM。
Q33：如果两个任务都修改同一个 Wiki 页面，并且没有依赖关系，会有什么风险？怎么改进？
风险是并发写冲突或后写覆盖先写。可以在 Plan 阶段合并同页任务，也可以在运行时加页面级锁，或者让 DAG 自动按 wiki_page 建立互斥依赖。

七、checkpoint / 恢复

Q34：checkpoint 的 namespace 为什么用 commit_hash？
commit_hash 能把一次提交对应的工作流状态隔离开，避免不同提交的 Analyze/Plan/Write 结果互相污染。同一个 revision 重跑时又能找到之前留下的断点。
Q35：phase 级 checkpoint 和 DAG task 级 checkpoint 有什么区别？
phase 级 checkpoint 保存整个阶段输出，适合 serial/parallel/pipeline 的阶段恢复。DAG task 级 checkpoint 保存单个任务结果，适合 Write 这种多任务阶段，失败后只重跑未完成任务。
Q36：为什么 checkpoint 里还要保存 session_path？
value 表示已完成结果，session_path 表示子 Agent 的会话文件。若任务中断但有会话记录，可以从 session_path 恢复上下文，而不是完全从头开始。
Q37：如果 50 个 Writer 任务执行到第 47 个失败，下次重跑会发生什么？
已完成的 46 个或 47 个任务会命中 task checkpoint，直接作为 seed 或缓存结果跳过；只有失败和未完成的任务会重新执行，大幅减少 LLM 成本和等待时间。
Q38：workflow 成功后为什么要清理 checkpoint？什么情况下会保留？
成功后清理可以避免旧状态影响后续运行，也减少磁盘垃圾。调试、失败恢复或请求传入 keep_checkpoint 时可以保留，用于分析中间结果。
Q39：如果 workflow YAML 改了，但 commit hash 没变，旧 checkpoint 会不会造成错误恢复？
有这个风险。当前 namespace 主要按 commit 隔离，如果 workflow 逻辑变了但 namespace 不变，可能复用旧阶段结果。改进方式是在 checkpoint meta 中加入 workflow 名称、脚本 hash 或版本，发现不一致就失效。

八、结构化输出

Q40：output_schema 是在哪里被转成 JSON Schema 的？
YAML 工作流先被 AST compiler 解析，output_schema 简写会被编译成标准 JSON Schema，并作为 schema 传给 agent(...)。运行时 WorkflowAgent.run() 根据 schema 注入 structured_output 工具。
Q41：Planner 为什么必须走结构化输出？
Planner 的输出会直接驱动后续 Writer 任务和 DAG 调度，必须机器可读。结构化输出可以保证字段如 wiki_page、section、action、instructions 明确存在，避免解析自由文本。
Q42：如果模型没有调用 structured_output 工具怎么办？
当前 WorkflowAgent.run() 会优先检查 capture；如果没有捕获到结构化输出，就退回取最后 assistant 文本。这说明任务没有满足契约，实际生产中应当把这种情况视为错误或触发重试。
Q43：结构化输出能解决所有幻觉问题吗？还需要什么？
不能。结构化输出只能保证形状稳定，不保证内容真实。还需要 source 约束、文件读取工具、质量检查器、结构断言、LLM Judge 和人工审查来降低事实错误。
Q44：capture.value 是怎么从工具调用里返回给 workflow 的？
create_structured_output_tool() 的 execute 函数会把工具参数写入 capture.value 并设置 capture.called = True。子 Agent prompt 结束后，WorkflowAgent.run() 检查 capture 并直接返回该结构化对象。

九、并发与异常

Q45：run_workflow() 里的 semaphore 控制了什么并发？
它控制同时运行的子 Agent 数量。即使 workflow 里 parallel 或 DAG 同时产生很多任务，进入 _agent() 时也要通过 semaphore，避免过多 LLM 请求导致限流或资源占用过高。
Q46：parallel() 和 dag() 都用了 asyncio.gather，两者区别是什么？
parallel() 只是把一组独立 thunk 一起跑；dag() 需要先校验依赖、检测环、按入度生成 ready 批次，并处理失败依赖和 seed 恢复。DAG 是有依赖约束的并发。
Q47：_agent() 捕获异常后为什么返回 None，而不是直接抛出？
这样单个 Agent 失败不会立刻把整个运行时打崩，DAG/parallel 可以记录失败并继续处理可处理部分。代价是错误可能被结果 None 吞掉，所以需要日志、on_agent_end error 和上层结果检查配合。
Q48：这样做会不会掩盖错误？你会怎么设计错误传播？
会有风险。更稳妥的设计是返回结构化结果，例如 {ok, value, error}，或者区分可恢复错误和致命错误。最终 workflow result 中也应包含失败任务列表，让前端和调用方明确知道不是完全成功。
Q49：record / replay 模式下为什么要把 concurrency 降到 1？
record/replay 通常按调用顺序消费 trace。并发会让 LLM 调用顺序不确定，导致 replay 游标错位。降到 1 能保证记录和回放顺序稳定，便于复现问题。
Q50：如果多个 Agent 同时调用工具写文件，怎么避免冲突？
当前主要依赖 Planner 合并同页任务和 DAG 依赖控制。更强的方案是引入文件级/页面级锁、写前读版本校验、冲突检测和合并策略，或者让调度器按目标文件自动串行化。

十、可观测性与产品化

Q51：on_agent_start、on_agent_end、on_phase、on_event 分别对应前端哪些状态？
on_phase 表示进入 Analyze/Plan/Write 等阶段，on_agent_start/end 表示某个子 Agent 开始和结束，on_event 转发子 Agent 内部文本增量和工具调用事件。前端据此展示进度、日志和工具执行。
Q52：如何定位一次 workflow 卡住是 LLM 慢、工具卡住，还是 DAG 依赖没释放？
先看最后一个 SSE 事件：停在 agent_start 可能是 LLM 或工具慢；有 tool_execution_start 没有 end 可能是工具卡住；DAG 没有新 agent_start 可能是依赖未满足或任务都失败。再结合后端 logs、phase、agent_count 和 checkpoint 文件定位。
Q53：/api/activity 为什么需要？它和 _active 字典是什么关系？
/api/activity 给前端或桌面宠物展示“系统是否忙碌”。run_background() 创建 task 后把 id(task) -> label 写入 _active，任务完成后 done callback 删除，接口读取这个状态。
Q54：如果后台任务异常退出，_active 会不会泄漏？
正常不会，因为 add_done_callback 在任务完成、异常或取消时都会触发，执行 _active.pop(id(t), None)。除非进程直接崩溃，否则活跃状态会被清掉。
Q55：当前日志里哪些信息对排查 Agent 问题最有用？
最有用的是 project、revision、phase、agent label、schema 是否启用、active tools、agent start/end、异常 traceback、workflow result、checkpoint hit 和 session_path。这些能串起一次失败的上下文。

十一、设计取舍

Q56：为什么不用 LangChain / Dify / CrewAI 直接做？
这些框架能快速搭 Agent，但项目核心需求是 VCS diff、Wiki 章节索引、DAG、checkpoint、桌面端和评测闭环的深度集成。自研运行时可以更精确地控制任务结构、恢复策略和工具权限。
Q57：为什么用 YAML 描述 workflow，而不是直接写 Python？
YAML 对用户更友好，适合声明 phase、step、agent、schema 和执行模式。它降低了自定义工作流门槛，也方便做静态校验和 UI 展示。
Q58：为什么 YAML 又要编译成 Python AST，而不是解释执行 YAML？
AST 让运行逻辑可以复用 Python async 能力，同时能统一生成 checkpoint、并发、dag、pipeline 等代码。相比解释器分支判断，AST 生成更接近真实可执行脚本，也便于插入安全检查。
Q59：为什么不用数据库存 workflow 状态，而是用 .wiki/checkpoints？
文件式 checkpoint 简单、透明、便于调试，也跟项目目录绑定。对中小型项目足够。规模更大或需要多进程并发时，可以迁移到 SQLite 或服务端状态存储。
Q60：如果项目规模扩大到上千 Wiki 章节，你会怎么优化索引和调度？
索引层从 JSON 迁移到 SQLite/FTS，支持增量更新和快速查询；调度层增加页面级锁、优先级队列、批量 diff 摘要和 token budget；评测层增加采样和持续质量监控。

十二、开放追问

Q61：这个项目里你最满意的技术设计是什么？
我会讲 DAG + checkpoint + structured_output 的组合。它把 LLM 从自由文本生成器变成可调度、可恢复、可验证的执行单元，体现 Agent 工程化。
Q62：你觉得这个项目最大的问题是什么？
最大问题是并发写和状态一致性还可以更强，例如多个 Writer 修改同一页面、workflow 版本变化后的 checkpoint 失效、LLM Judge 稳定性等，都需要进一步工程化。
Q63：如果让你重构 run_workflow()，你会拆成哪些模块？
我会拆成 parser/meta、runtime context、agent runtime、scheduler(parallel/pipeline/dag)、checkpoint manager、sandbox executor、result/error model。这样测试更独立，也方便替换调度策略。
Q64：如果上线给团队使用，你会补哪些监控和测试？
监控方面补 token、耗时、失败率、模型错误、工具错误、checkpoint 命中率和队列事件。测试方面补 workflow 编译快照、DAG 边界、checkpoint 恢复、SSE 断连、并发写冲突和真实 case eval。
Q65：如果模型输出质量下降，你有哪些兜底策略？
先用结构化输出和 schema 降低格式风险；再用质量检查、LLM Judge 和规则校验发现问题；必要时切换模型、降低并发、增加重试、自检 prompt、人工确认高风险修改，或回滚 Wiki 变更。
