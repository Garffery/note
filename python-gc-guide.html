1. 先记住这几个核心结论

主机制

CPython 主要依靠引用计数管理对象生命周期。

补充机制

循环垃圾回收器专门处理容器对象形成的引用环。

内存不一定下降

对象释放后，内存可能留在 Python 分配器或进程堆中复用。

一句话模型 CPython 的垃圾回收可以理解为“引用计数负责日常回收，循环 GC 负责清理引用计数无法处理的环”。

“Python 的 GC”容易被误解为一个统一机制。实际上要分三层理解：

  1. 语言层：Python 规范描述对象何时变得不可达，但通常不保证资源会在哪个精确时刻释放。
  2. 实现层：CPython、PyPy 等实现采用不同的内存管理策略；本文主要讨论 CPython。
  3. 操作系统层：Python 对象被销毁，不等于对应的进程内存会立刻归还操作系统。

2. 引用计数：CPython 的第一道回收机制

在 CPython 中，每个对象都维护引用计数。新增一个强引用时计数增加，引用消失时计数减少；计数变为 0 后，对象通常立即进入销毁流程。

变量 a ─┐ ├──▶ 对象 [1, 2, 3] 引用计数 = 2 变量 b ─┘ del a → 引用计数 = 1 del b → 引用计数 = 0 → 对象可被释放

哪些操作会影响引用计数？

操作典型影响示例
创建或赋值引用增加b = a
放入容器增加items.append(a)
函数传参调用期间通常增加func(a)
删除变量或覆盖变量减少del a、a = None
从容器移除减少items.pop()
离开作用域局部引用减少函数返回
 
import sys

obj = []
print(sys.getrefcount(obj))
# getrefcount(obj) 调用本身会临时增加一次引用，结果通常比直觉多 1

优势与局限

  • 优势：对象往往能及时销毁，生命周期较直观，回收工作被分散到程序运行过程中。
  • 局限：维护计数有成本；多线程环境需要保证计数更新安全；最关键的是无法单独处理循环引用。
不要依赖“立即销毁”编写跨实现代码CPython 经常能在引用计数归零时立即终结对象，但其他 Python 实现可能延迟回收。文件、锁、数据库连接等资源应使用 with 或显式关闭。

3. 循环垃圾回收：引用环如何被发现

两个或多个对象相互引用时，即使程序已经无法访问它们，各自的引用计数仍可能大于 0。循环 GC 会跟踪可能参与引用环的容器对象，并周期性寻找不可达环。

class Node:
    def __init__(self, name):
        self.name = name
        self.peer = None

left = Node("left")
right = Node("right")
left.peer = right
right.peer = left

del left, right
# 两个对象互相引用，但外部已无法访问；需要循环 GC 识别

核心思路：扣除内部引用后重算可达性

循环 GC 不等引用计数归零，而是换一个角度问：“除了这个圈子内部，还有没有别的引用指向它们？”

  1. 复制引用计数。把候选对象的引用计数复制一份，专供本次计算使用。
  2. 扣除内部引用。减掉候选对象之间的互相引用，剩下的就是来自外部的引用。
  3. 划分可达与不可达。仍有外部引用（或被可达对象引用）的存活，其余判定为不可达并清理。

把这套判断放进“分代”的调度框架里执行，就是下一节的完整流程。

哪些对象会被 GC 跟踪？通常是可能持有其他对象引用的容器，例如列表、字典、集合、类实例。整数、字符串等简单原子对象通常不需要循环 GC 跟踪。CPython 还可能对只包含不可跟踪对象的容器进行优化。
import gc

print(gc.is_tracked([]))       # 通常为 True
print(gc.is_tracked(42))       # 通常为 False
print(gc.is_tracked({}))       # 空字典可能未被跟踪（实现优化）
print(gc.is_tracked({"x": []})) # 包含容器后通常被跟踪

4. 分代回收：为什么年轻对象查得更频繁

分代假说认为：“大多数对象生命周期很短，而存活较久的对象往往会继续存活。”因此 GC 更频繁地扫描新对象，避免每次都把长期存活的对象重新扫一遍。

gen0 年轻代

新分配、被 GC 跟踪的容器先进这一代；扫描最频繁。

gen1 中年代

在年轻代回收中幸存的对象晋升到这里；扫描频率低一档。

gen2 老年代

存活最久的一批；扫描最少，幸存者留在本代不再晋升。

4.1 代是怎么组织对象的

每个被 GC 跟踪的对象都带有一个 GC 头，记录它属于哪一代、同代链表中的前后指针、回收期间使用的引用计数副本，以及“正在被收集”“已终结”等标志位。所有跟踪对象按代挂在几条双向链表上，一次“收集”本质上就是遍历其中一条或多条链表。

新分配、被 GC 跟踪的容器对象 │ 建立 GC 头，挂入 gen0 ▼ gen0 年轻代 ── 扫描最频繁 │ 幸存者晋升 ▼ gen1 中年代 ── 扫描频率低一档 │ 幸存者晋升 ▼ gen2 老年代 ── 扫描最少；幸存者留在本代
  • 入代：容器对象被 GC 跟踪时进入 gen0，从此参与循环 GC 的扫描。
  • 合并：收集第 N 代时，比它更年轻的几代会被并入同一次扫描，一起判断存活与否。
  • 出代：判定不可达的对象在本轮被清理；幸存者在回收结束时被并入更老的一代。

4.2 什么时候触发、收集哪一代

GC 维护“自上次回收以来被跟踪对象的净分配量”：分配加一、释放减一，按代分别记录。触发与选代规则可以概括成下表。

条件行为
count0 超过 threshold0启动一次回收，默认只检查最年轻的第 0 代。
自第 1 代上次被检查以来，第 0 代已被检查超过 threshold1 次本次回收把第 1 代一并纳入扫描范围。
更老一代的检查次数继续累积达到 threshold2把最老的第 2 代也纳入，等价于一次全量回收。
threshold0 设为 0关闭自动回收，只剩手动 gc.collect()。

默认阈值 (700, 10, 10) 的含义：年轻代每累计大约 700 个净分配就回收一次；它大约被检查 10 次，才会顺带扫一次第 1 代；第 1 代同理累积到 10 次，才带动最老的一代。这就是“年轻代回收最频繁、全量回收最少见”的来源。

第 2 代的纳入条件比前两代更复杂，官方文档把它单独拿出来讨论（“收集最老一代”），并在不同版本中调整过策略——3.14 系列还一度把它改成增量推进。实际节奏请以运行版本的 gc.get_count()、gc.get_threshold()、gc.get_stats() 为准。

import gc

print(gc.get_count())      # (count0, count1, count2)：净分配量，不是对象总数
print(gc.get_threshold())  # (700, 10, 10)

gc.set_threshold(700, 10, 10)
# 修改阈值前先监控和压测；默认值对多数应用是合理的

gc.collect()  # 手动全量回收，返回 回收对象数 + 不可回收对象数
自动回收是同步发生的它在分配对象的路径上被触发，直接跑在触发它的那个线程里，不会交给后台线程。因此回收耗时会计入本次请求的延迟——这正是需要监控 GC 停顿的原因。

4.3 一次年轻代回收的完整流程

下面把一次回收拆成八个阶段。括号里的函数名对应 CPython Modules/gcmodule.c 的实现，便于按名字检索源码；概念顺序在各个 3.x 版本中保持一致。

① 触发 count0 超过 threshold0，在分配路径上同步发生 │ ② 选定代数 从年轻代开始逐个检查阈值；选中的第 N 代连同更年轻的代一起构成候选集合 │ ③ update_refs 把每个候选对象的 ob_refcnt 复制到 GC 头的 gc_refs │ ④ subtract_refs 扣除候选集合内部的互相引用；剩下的 gc_refs 就是外部引用数 │ ⑤ move_unreachable gc_refs 大于 0 的对象标为可达并传播标记；gc_refs 为 0 的移入 unreachable 链表 │ ⑥ 弱引用与终结器 清空指向不可达对象的弱引用并回调；调用 __del__/tp_finalize；处理对象复活 │ ⑦ 断开并释放 先用 tp_clear 断开不可达对象之间的引用，再让引用计数逐一归零、释放内存 │ ⑧ 晋升与清零 幸存者并入更老的一代；被收集各代的计数清零，回收结束
  1. 触发：净分配量超过阈值。分配或释放被跟踪对象时更新 gen0 计数；count0 超过 threshold0，就在分配路径上启动本次回收。
  2. 选代：确定这一轮扫到哪一代。从最年轻的代开始检查阈值，命中后把该代与所有更年轻的代合并成候选集合（gc_list_merge）；gc.collect(2) 这类调用会直接指定全量收集。
  3. update_refs：复制引用计数。遍历候选集合，把真实的 ob_refcnt 复制到 GC 头的 gc_refs。此后所有加减只作用于副本，真实计数不会被计算过程弄脏。
  4. subtract_refs：扣除集合内部的互相引用。遍历候选对象的每条引用，若被引用者也在候选集合中，就把它的 gc_refs 减一。全部走完后，gc_refs 表示“来自候选集合外部的引用数量”。
  5. move_unreachable：划分可达与不可达。gc_refs 大于 0 的对象一定还有外部引用，标为可达，并从它们出发把能到达的对象一并标记；gc_refs 为 0 且没有被标记到的对象移入 unreachable 链表——它们已经无法从外界访问，只是被环圈住了。
  6. 弱引用与终结器：按 PEP 442 的顺序处理。先清空指向不可达对象的弱引用并触发其回调（此刻这些对象仍然可用），再调用 __del__ / tp_finalize（同一集合内的调用顺序不做保证）。如果某个对象在终结过程中复活、重新变得可达，整个不可达集合会被放回，本轮回收放弃。
  7. 断开引用并释放。确认没有复活之后，不可达对象成为“循环垃圾”：先用 tp_clear 断开它们彼此持有的引用，避免深层递归和释放顺序问题，随后引用计数逐一归零，内存被释放。
  8. 晋升与收尾。幸存对象并入更老的一代（gen0 → gen1、gen1 → gen2，第 2 代的幸存者留在原地）；被收集各代计数清零，统计写入 gc.get_stats()，然后等待下一次触发。
为什么要多一份 gc_refs判断可达性需要临时“扣除”集合内部的引用，但真实引用计数是对象的命根子，不能被计算过程干扰。把 ob_refcnt 复制到 GC 头后再做加减和标记，回收结束后真实计数依然准确。

4.4 老年代回收与全量回收

  • 候选集合更大：收集第 N 代会连带更年轻的代一起扫描，gc.collect(2) 需要遍历全部被跟踪对象。
  • 停顿更长：对象更多、引用更密，扫描耗时通常明显大于年轻代回收，低延迟服务在意的往往就是它。
  • 触发策略更保守：最老一代不是简单按阈值计数，官方文档对它单独描述；3.14 系列还一度把它改成增量推进，把一次长停顿摊到多次回收中。
  • 版本差异明显：3.14.5 起第 1 代与 threshold2 被恢复，行为重新对齐 3.13。判断线上节奏要看实测数据，而不是照搬资料里的数字。

4.5 晋升、永久代与观测分代行为

晋升规则可以记成三句话：回收中幸存的对象被并入更老的一代；第 2 代已经是最老的一代，幸存者留在原地；只有真正被回收扫描过并幸存，才会晋升。

gc.freeze() 提供另一条路：把当前全部被跟踪对象移入永久代，之后的回收直接忽略它们。gc.unfreeze() 把它们放回最老的一代，gc.get_freeze_count() 查看永久代对象数量。典型用法是在 Unix fork() 之前冻结：模块级对象不再参与回收，也就不会反复触发写时复制，子进程的内存共享更好。

import gc

class Payload:
    pass

def count_in(generation):
    return sum(isinstance(obj, Payload) for obj in gc.get_objects(generation))

gc.collect()                            # 先清一遍历史垃圾，便于观察
alive = [Payload() for _ in range(5)]    # 保留强引用，否则会被引用计数立即回收

print("刚创建:", count_in(0))            # 新对象位于 gen0
gc.collect(0)                            # 年轻代回收：幸存者晋升 gen1
print("gen0 回收后:", count_in(0), count_in(1))
gc.collect(1)                            # 第 1 代回收：幸存者晋升 gen2
print("gen1 回收后:", count_in(1), count_in(2))

# 注意：3.14.0–3.14.4 取消了第 1 代，get_objects(1) 不返回对象；3.14.5 起恢复。
3.14 系列：同一个大版本内也不一样3.14.0–3.14.4 取消第 1 代、改为两代模型并支持老年代增量收集：gc.get_objects(1) 不返回对象，gc.collect(1) 表示“推进一次增量收集”，threshold2 被忽略。3.14.5 起第 1 代和 threshold2 恢复，行为重新对齐 3.13。背诵“三代”或“两代”都不稳妥，用 gc.get_threshold() 和实测结果确认才准确。

5. 可达性分析：Python 和根集合算法的区别

JVM、.NET、Go、V8 这些主流运行时判断对象是否该回收时，做的都是同一件事：从根集合出发沿引用标记，标记不到的就是垃圾。CPython 走的却是另一条路——它不枚举根，而是把引用计数当作“入度统计”，在候选集合内部做一次减法，反推“还有没有来自外部的引用”。这一节讲清这个区别，以及它换来了什么、失去了什么。

根集合算法（JVM / Go / V8 / .NET） 根集合：线程栈、寄存器、静态区、句柄表 │ 从根出发沿引用标记 ▼ 标记完的可达对象 没有标记到的 = 垃圾 ───────────────────────────────────────────────────── CPython 候选集合：某一代里被跟踪的对象 │ 用引用计数扣除集合内部的互相引用 ▼ 差值仍为正 → 有外部引用 → 存活 差值归零且传播不到 = 垃圾

5.1 两大家族

把常见的垃圾回收实现按“怎么确定对象不可达”分类，能看清 Python 的位置。

家族代表环怎么处理关键前提
精确追踪式JVM（G1/ZGC）、.NET、V8、Go可达性天然覆盖环，不需要额外机制编译器/JIT 提供精确栈映射，配套写屏障

5.2 CPython 的做法：用引用计数替代根集合

为什么可以不枚举根？因为引用计数本身就是一份精确的入度统计：只要还有引用存在——无论是模块字典、栈帧、容器，还是 C 代码里的变量——引用计数都会体现出来（前提是扩展遵守 INCREF/DECREF 规则）。于是“谁还有外部引用”不需要扫描内存就能算出来：

  1. 把候选集合里每个对象的引用计数复制一份（gc_refs）。
  2. 扣除候选对象之间的互相引用。
  3. 差值仍为正的对象，一定存在来自集合外部的引用——它可能直接就是一个根，也可能是老一代对象、未跟踪容器或 C 层引用。
  4. 从这些对象出发传播标记，没被标记到的就是垃圾。
关键结论CPython 不需要扫描 C 栈和寄存器，也不要求扩展暴露对象布局，只需要它们遵守引用计数规则。这正是它能和任意 C 扩展共存的原因——换成精确追踪式，就必须为每一段 C 代码提供栈映射，这在实践中做不到。

但这套判断只在候选集合内部成立。收集年轻代时，老一代对象天然被当成“外部引用”，所以跨代的环会多活一段时间，直到某次全量回收才被处理。

import gc

class Node:
    pass

# 情形一：纯粹的环，没有任何外部引用
a = Node(); b = Node()
a.peer = b
b.peer = a
del a, b          # 环内互相引用，两个对象的引用计数都还大于 0
gc.collect()      # 扣除内部引用后差值为 0 → 判定为垃圾

# 情形二：同样的环，但外部还留着一个引用
c = Node(); d = Node()
c.peer = d
d.peer = c
keep = c          # 模块全局引用，属于“候选集合外部”
del c, d
gc.collect()      # 差值仍为正 → 整圈存活

5.4 优点：这些差异换来了什么

  • C 扩展友好：不需要扫描 C 栈与寄存器，也不要求扩展暴露对象内部布局，只要守住引用计数规则即可——这是决定性的工程优势。
  • 回收及时、成本分散：无环对象在最后一个引用消失的瞬间销毁，内存峰值低，回收开销摊在整个程序生命周期里，而不是集中在一次停顿中。
  • 终结时机可预期：__del__、文件与锁的关闭、weakref 回调大多在可预期的时刻发生，这让隐式清理比“终结器队列”模型可靠得多。
  • 扫描范围小：整数、字符串等原子对象不进 GC 链表，环检测只扫“可能成环”的容器对象。
  • 对象地址稳定：可以放心把指针交给 C 代码，id() 在对象生命周期内稳定，不需要 pin 或句柄间接层。
  • 不需要预留腾挪空间：没有 survivor space、也没有“为 GC 预留 100% 堆”这类机制（对比 Go 的堆目标、JVM 的分代预留）。
  • 实现与调试更简单：没有写屏障、卡表、并发标记状态机这些部件，行为更容易预测和观测。

5.5 缺点：差异在哪里咬人

  • 环必须靠周期性扫描：引用计数替代不了环检测，而它默认是同步停顿，成本随被跟踪对象数增长。3.14.0–3.14.4 曾把老年代改成增量推进，3.14.5 又回退到与 3.13 一致的行为。
  • 引用计数的持续开销：每次赋值、传参、入容器都要更新计数，写放大明显、缓存局部性差；多线程下还要保证更新安全，自由线程构建因此用偏置引用计数、并把 PEP 683 的 immortal 对象排除在计数之外。
  • 没有写屏障 → 没有“老 → 新”引用记录：年轻代回收只能把老对象的引用一律视为外部引用，跨代浮动垃圾会多活；老年代回收也只能整体扫描，做不到 JVM 卡表那样的分区回收。
  • 不移动对象 → 不能整理碎片：pymalloc 的 arena 只有整体空闲时才可能归还系统，所以 RSS 常年不降；也无法使用复制式新生代回收——而那是停顿最短的回收方式。
  • 停顿不并发：默认构建下回收在分配路径上同步发生，堆越大停顿越明显；这也是低延迟服务关注 GC 监控的原因。
  • 每对象开销与两次遍历：被跟踪对象都要带 GC 头，一轮回收至少要遍历引用两遍（subtract_refs 与 move_unreachable）。
  • 正确性负担转嫁给扩展作者：漏掉 INCREF/DECREF 会直接崩溃或泄漏；追踪式 GC 里漏写屏障通常只是延迟回收，不会立即崩。
  • 两套机制、诊断更复杂：既要排查引用计数型泄漏（全局容器、闭包、traceback），又要排查环型垃圾（含“容器未实现遍历接口”导致回收不到的情况）。

5.6 同类实现：PHP、Perl、Swift 各走了一步

  • PHP：同样是“引用计数 + 环收集器”，思路与 CPython 最接近，但收集器以增量方式运行、由“可能的根”缓冲区驱动，把停顿切得更碎。
  • Perl 5：在引用计数之上做的是从根出发的周期性标记清除，需要扫描解释器栈与符号表，因此更像经典追踪式。
  • Swift / Objective-C：只有 ARC，没有环收集器，环必须靠 weak/unowned 手动打破——这是“纯引用计数”路线的必然结果。
  • Boehm GC：保守式追踪，不需要编译器配合，代价是不能移动对象，还可能因为把整数误认成指针而多留垃圾。
  • PyPy：换成从根出发的增量分代标记清除，终结时机与 CPython 不同——这正是文档反复提醒“不要依赖作用域结束就立即释放资源”的原因。

5.7 实践上怎么用这些差异

  • 长驻服务：RSS 不降通常来自分配器与碎片，而不是“GC 不工作”；跨代浮动垃圾会把内存峰值拉长。先用 gc.get_stats() 和 tracemalloc 看清事实，再考虑阈值。
  • 延迟敏感：CPython 的回收成本分散在赋值操作上，通常比一次集中停顿更平滑；真正需要防的长停顿来自老年代与全量回收。
  • 原生内存：GC 只看得见 Python 对象，malloc、NumPy、GPU 缓冲有各自的分配器与缓存，需要单独的限制与释放策略。
  • 容量对比：JVM/Go 服务有压缩与并发标记，长时间运行后的内存形态和 Python 差别很大，不能直接类比。

6. gc 模块常用 API

API用途注意事项
gc.collect(generation=2)执行一次回收；默认 2 表示全量回收，返回“回收对象数 + 不可回收对象数”。generation 必须在 0–2 之间，否则抛 ValueError；回收进行中再调用行为未定义；代编号含义存在版本差异。
gc.enable() / gc.disable()启用或停用自动循环 GC。不影响引用计数。
gc.isenabled()查看自动 GC 是否开启。适合诊断运行环境。
gc.get_count()读取各代计数，即自上次回收以来的净分配量。不能直接等同于对象数量。
gc.get_threshold() / set_threshold()读取或调整自动回收阈值。threshold0=0 会关闭自动回收。
gc.get_stats()读取各代累计回收统计。返回字典列表，包含 collections、collected、uncollectable。
gc.get_objects()获取 GC 正在跟踪的对象，可用 gc.get_objects(0) 只取某一代。开销和结果规模可能很大；3.14.0–3.14.4 中第 1 代不返回对象。
gc.get_referrers(obj)查找直接引用目标的 GC 容器。只适合调试；返回值可能包含临时或未完全初始化对象。
gc.get_referents(obj)查看对象通过 GC 遍历接口引用的对象。不保证列出所有语言层引用。
gc.is_tracked(obj)判断对象是否被循环 GC 跟踪。结果受类型和实现优化影响。
gc.set_debug(flags)开启回收调试输出或保存不可达对象。生产环境慎用。
gc.callbacks在 GC 开始和结束时执行回调。回调必须轻量，避免递归触发和明显阻塞。
gc.freeze() / unfreeze() / get_freeze_count()把当前所有跟踪对象移入永久代（后续回收忽略它们）、放回最老一代、查看永久代对象数。常见于 Unix fork() 前的写时复制优化；Python 3.7 起提供。

监控 GC 停顿和回收结果

import gc
import time

starts = {}

def on_gc(phase, info):
    generation = info["generation"]
    if phase == "start":
        starts[generation] = time.perf_counter()
    else:
        elapsed_ms = (time.perf_counter() - starts.pop(generation, time.perf_counter())) * 1000
        print(
            f"GC gen={generation}: {elapsed_ms:.2f} ms, "
            f"collected={info['collected']}, uncollectable={info['uncollectable']}"
        )

gc.callbacks.append(on_gc)

7. __del__、上下文管理器与弱引用

不要把 __del__ 当成可靠的资源管理工具

__del__ 是终结器，不等同于 C++ 的确定性析构函数。它可能在解释器关闭阶段执行，也可能因对象复活、模块全局变量已被清理等因素产生复杂行为。现代 CPython 可以安全处理许多含 __del__ 的引用环，但终结逻辑依然应尽量简单。

# 推荐：资源生命周期清晰、异常时也能关闭
with open("data.txt", "r", encoding="utf-8") as file:
    content = file.read()

# 对自定义资源，优先实现 __enter__ / __exit__ 或提供 close()

弱引用 weakref

弱引用允许引用对象但不增加其强引用计数。目标没有强引用后仍可被回收，适合缓存、观察者列表和对象映射等场景。

import weakref

class User:
    pass

user = User()
user_ref = weakref.ref(user)
assert user_ref() is user

del user
assert user_ref() is None

# 常用弱引用容器：
cache = weakref.WeakValueDictionary()

weakref.finalize(obj, callback, ...) 通常比手写 __del__ 更容易管理清理回调，但它也不是替代 with 的理由。

8. 内存泄漏与持续增长：如何系统排查

Python 中所谓“内存泄漏”至少有三种情况，必须先区分：

  • 仍被引用的对象持续累积：无界缓存、全局容器、消息队列、回调、闭包、日志处理器等。
  • 对象已释放但内存未归还操作系统：分配器保留 arena、堆碎片化或底层库缓存。
  • C 扩展或本地资源泄漏：Python GC 看不到或无法修复底层分配错误。

推荐排查路径

  1. 建立稳定复现。固定输入和并发，持续记录 RSS、Python 堆大小、对象数与请求量。
  2. 判断是否为 Python 对象增长。使用 tracemalloc 比较快照；必要时使用对象图工具。
  3. 定位增长的分配位置。按文件、行号和 traceback 分组，关注持续增长而非一次性峰值。
  4. 寻找保留路径。检查全局字典、LRU 缓存、任务集合、异常 traceback、闭包和监听器。
  5. 验证修复。用同一负载做前后对比，观察对象是否进入稳定平台，而不是只看一次 gc.collect()。

用 tracemalloc 比较快照

import gc
import tracemalloc

tracemalloc.start(25)
before = tracemalloc.take_snapshot()

# 运行怀疑会导致内存增长的业务操作
run_workload()

gc.collect()
after = tracemalloc.take_snapshot()

for stat in after.compare_to(before, "lineno")[:15]:
    print(stat)

调试不可达对象

import gc

gc.set_debug(gc.DEBUG_SAVEALL)
unreachable = gc.collect()
print("unreachable:", unreachable)
print("saved in gc.garbage:", len(gc.garbage))

# 调试完成后必须清理保存列表，否则 DEBUG_SAVEALL 本身会保留对象
gc.garbage.clear()
gc.set_debug(0)
gc.collect() 后 RSS 不降，不等于 GC 失效CPython 的小对象分配器会复用内存池；只有满足条件的完整 arena 才可能归还系统。某些 C 库也会维护自己的缓存。应同时观察 tracemalloc、对象数量和 RSS。

9. GC 性能调优：什么时候值得动参数

默认配置对大多数应用已经合理。调优前先测量 GC 次数、停顿时长、回收对象数和业务延迟；不要仅因“GC 听起来慢”就关闭它。

场景可考虑的措施主要风险
大量短命容器，GC 触发过频基准测试后适当提高阈值。垃圾对象驻留更久，内存峰值上升。
低延迟关键区间短暂禁用自动 GC，区间结束后恢复并选择合适时机回收。异常路径未恢复；循环垃圾快速累积。
长期进程的缓存增长优先限制缓存容量、设置过期策略。调 GC 参数通常治标不治本。
Unix 服务 fork 子进程按官方建议组合 gc.disable()、gc.freeze() 与 fork。平台相关，流程错误会增加内存。
数值计算占用巨大检查 NumPy/PyTorch 等底层分配器和设备缓存。gc 只看到 Python 包装对象。

安全地临时关闭自动 GC

import gc

was_enabled = gc.isenabled()
try:
    if was_enabled:
        gc.disable()
    latency_sensitive_work()
finally:
    if was_enabled:
        gc.enable()

# 是否主动 collect 应由延迟预算和实测决定
关闭循环 GC 不会关闭引用计数绝大多数无环对象仍会在引用计数归零后被释放；被延迟处理的是循环垃圾。

10. 工程最佳实践清单

  • 使用 with 管理文件、Socket、锁、数据库事务和外部资源。
  • 为缓存设置容量上限、TTL 或淘汰策略，避免无界字典。
  • 任务完成后移除回调、监听器、Future、后台任务和全局注册项。
  • 避免让长生命周期对象意外捕获大对象，例如闭包、异常 traceback 和默认参数。
  • 需要非拥有关系时考虑 weakref，但不要为了“消灭所有环”牺牲清晰设计。
  • 用指标与基准测试指导阈值调整，并记录 Python 版本和实现。
  • 分析内存时区分 Python 堆、C 扩展内存、设备内存和进程 RSS。
  • 不要在高频路径调用 gc.get_objects() 或 gc.get_referrers()。
  • 不要把定时 gc.collect() 当成通用修复；它会引入全局扫描和延迟抖动。

11. 高频面试问答

Python 的垃圾回收机制是什么？
如果限定 CPython：主要是引用计数，辅以分代的循环垃圾回收器；引用计数负责大多数对象的及时销毁，循环 GC 负责查找容器对象形成的不可达引用环。
del x 会删除对象吗？
del x 删除的是名称与对象之间的绑定。只有当这次操作使对象不再有强引用时，对象才可能被销毁；若仍被其他变量或容器引用，对象会继续存在。
为什么循环引用不能仅靠引用计数回收？
环内对象相互持有强引用，即使外部已经不可达，每个对象的引用计数仍大于 0，因此需要循环 GC 根据“外部可达性”识别整个不可达集合。
分代回收中一次回收的完整流程是什么？
净分配量超过 threshold0 触发回收；按阈值选出要收集的代数，并把更年轻的代并入候选集合；先把每个候选对象的引用计数复制成 gc_refs，再扣掉集合内部的互相引用，剩下的就是外部引用数；gc_refs 为 0 且无法从可达对象传播到达的对象判定为不可达；随后依次清空弱引用并回调、调用终结器、处理对象复活，最后断开不可达对象之间的引用并释放内存；幸存者晋升到更老的一代，被收集各代的计数清零。
Python 的可达性分析和 JVM、Go 的根集合标记有什么区别？
JVM、Go、V8 都从根集合（线程栈、寄存器、静态区、句柄）出发做精确标记，需要编译器或 JIT 提供栈映射，并依赖写屏障维护跨代/并发标记的状态。CPython 不枚举根，而是把引用计数当作入度统计：在候选集合内部扣除互相引用，差值仍为正就说明存在外部引用，从这些对象传播标记，其余判定为垃圾。好处是不用扫描 C 栈和寄存器，天然兼容任意 C 扩展；代价是无法整理碎片、没有“老→新”引用记录（跨代浮动垃圾会多活）、环检测只能周期性同步停顿。同类实现里 PHP 最接近，Perl 5 走的是从根标记清除，Swift/ARC 则完全没有环收集器。
执行 gc.collect() 为什么进程内存没有下降？
对象空间可能被 Python 分配器保留以便复用，底层堆可能碎片化，或内存来自 C 扩展和外部库。对象被回收与 RSS 立即下降不是同一件事。
如何避免 Python 内存泄漏？
限制缓存，及时解除全局注册和回调，使用上下文管理器关闭资源，监控长生命周期容器，并通过 tracemalloc 快照和引用路径定位真正的保留者。
gc.disable() 后 Python 还会释放对象吗？
在 CPython 中会。它只关闭自动循环 GC，引用计数仍然工作；但不可达引用环会继续积累，除非重新启用或手动回收。
弱引用的典型用途是什么？
用于不应延长目标生命周期的关系，例如缓存值、观察者、对象注册表、父对象反向引用等。目标被回收后，弱引用返回 None，弱引用容器会自动移除相应条目。

12. 版本与实现差异

  • CPython：以引用计数加循环 GC 为核心。本文绝大多数行为描述针对 CPython。
  • PyPy：通常采用追踪式垃圾回收，对象终结时机与 CPython 不同；不要依赖引用离开作用域后资源立即关闭。
  • Python 3.14 系列：3.14.0–3.14.4 取消第 1 代、改为两代模型并支持老年代增量收集（collect(1) 表示推进一步，threshold2 被忽略，get_objects(1) 为空）；3.14.5 起第 1 代与 threshold2 恢复，重新对齐 3.13。
  • 自由线程 CPython：自动回收还会参考内存增长：若内存较上次回收增长不足 10%，且净分配量未超过 40 × threshold0，就跳过本次回收；调优时应核对对应版本的官方文档。
阅读资料时先看版本GC 属于实现细节较多、持续演进的领域。生产调优应以目标 Python 版本的官方文档、真实指标和基准测试为准。
