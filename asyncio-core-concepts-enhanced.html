0开篇导读

asyncio 的核心抽象只有三个：协程（Coroutine）是"做什么"，任务（Task）是"由谁来做、做到哪了"，Future（未来）是"结果占位符"。三者层层递进，理解它们的关系就等于拿到了 asyncio 的钥匙。

为什么要搞懂这三者？

很多开发者能写出 async def，但一遇到 Task、Future、gather、wait_for 就懵。根本原因是把"协程对象"和"正在运行的任务"混为一谈，也不清楚 Future 在底层扮演的角色。本课的目标就是把这个认知补齐。

学完本课你将能：准确区分三种对象、看懂调度机制、做出正确选型、避开高频踩坑点，并为后续 gather、wait、同步原语打下基础。

1三者定义与关系

1.1 一句话定义

概念通俗解释角色类比
协程async def 定义的函数返回的对象，可暂停/恢复的计算单元📝 一份待执行的菜谱
任务 Task把协程包装并附加调度信息，与事件循环绑定的对象，管理协程生命周期👨‍🍳 厨师：拿菜谱按循环指令做菜、暂停、完成
Future一个占位符，代表未来某时刻才有的结果，提供回调注册机制🧾 取餐号牌："菜还在做，凭此取"

1.2 关系图解（增强版）

图 1-1　协程 → Task → Future 的继承与调度关系
关键点（必须记住）
  • Task 是 Future 的子类 → Task 拥有 Future 全部能力：.done()、.result()、add_done_callback()，并额外增加了协程调度能力。

1.3 三者的创建方式

Python
import asyncio

# ① 协程对象 —— 调用 async def 函数得到
async def my_coro():
    return 42

coro = my_coro()          # 此时只是创建了对象，尚未运行
print(type(coro))       # <class 'coroutine'>

# ② 任务：把协程包装成可调度的 Task

task = asyncio.ensure_future(my_coro()) # 旧用法，对协程也返回 Task

# ③ Future：底层/手动创建，代表"未来结果"

future = loop.create_future()          # 一个 pending 的 Future
易混点：协程对象 ≠ 正在运行 my_coro() 只是"造了一个对象"，里面一行代码都没执行。要让它跑起来，必须 await 它，或交给 create_task 让事件循环去驱动。这是初学者最常踩的坑。

2协程深度解析

2.1 协程对象的本质

async def 定义的是协程函数，调用它返回协程对象。协程对象实现了 __await__ 方法，因此是"可等待对象（awaitable）"。

验证
async def hello():
    return "world"

print(type(hello))              # <class 'function'>  ← 函数本身
coro = hello()
print(type(coro))               # <class 'coroutine'> ← 调用后才得到对象
print(hasattr(coro, '__await__'))  # True ← 可等待
核心特征
  • 协程对象只能被 await 一次，第二次 await 会抛 RuntimeError: cannot reuse already awaited coroutine。
  • 协程对象不直接与事件循环交互，需被 Task 包装或经 asyncio.run() 运行。

2.2 协程的四个状态

通过 inspect.getcoroutinestate(coro) 查看：

状态含义何时出现
CORO_CREATED已创建，尚未执行coro = my_coro() 之后
CORO_RUNNING正在执行进入协程体后
CORO_SUSPENDED遇到 await 被挂起在 await 处让出控制权
CORO_CLOSED执行完毕或异常退出return 或抛异常后
状态观察
import inspect, asyncio

async def demo():
    print("进入协程")
    await asyncio.sleep(0)      # 这里会挂起一次
    print("协程结束")

coro = demo()
print(inspect.getcoroutinestate(coro))   # CORO_CREATED
asyncio.run(coro)                          # 运行后变为 CORO_CLOSED
print(inspect.getcoroutinestate(coro))   # CORO_CLOSED
CORO_CREATED 进入协程 协程结束 CORO_CLOSED
图 2-1　协程状态流转：CREATED → RUNNING ⇌ SUSPENDED → CLOSED

2.3 协程能"裸跑"吗？

可以但不推荐：asyncio.run(coro) 能直接运行协程。但其内部会创建 Task 包装。看 asyncio.run 的简化源码：

asyncio.run 简化源码
def run(main):
    loop = new_event_loop()
    try:
        return loop.run_until_complete(main)  # main 是协程，内部会 ensure_future
    finally:
        loop.close()
结论：协程在事件循环中总是被包装成 Task 执行。"裸跑"只是省略了你手动包装的步骤。

2.4 协程的底层数据结构

C 层面，协程对象包含：

  • cr_frame：当前执行的栈帧
  • cr_running：是否正在运行
  • cr_code：协程的代码对象
  • 通过 await（本质是 yield from）实现挂起/恢复
为什么协程能"暂停"？
协程底层基于生成器（generator）。遇到 await 时，协程把控制权"yield"回事件循环，自己保存当前栈帧；事件循环稍后再用 .send() 把控制权还给它，从上次暂停处继续。这就是协程比线程轻量的原因——没有真正的线程切换开销，只是函数级别的"让出/恢复"。

3Task 精讲

3.1 Task 的作用

Task 在 asyncio 中承担调度单元角色：

  • 包装协程，提供状态管理（pending / done / cancelled）
  • 注册到事件循环，由循环驱动协程推进
  • 支持取消、超时、回调等操作
图 3-1　Task 的完整生命周期与状态转移

3.2 创建 Task 的三种方式

三种创建方式
async def work(n):
    await asyncio.sleep(n)
    return n

async def main():
    # ① asyncio.create_task() —— Python 3.7+ 推荐
    task1 = asyncio.create_task(work(1))

    # ② loop.create_task() —— 需要指定 loop 时用
    loop = asyncio.get_running_loop()
    task2 = loop.create_task(work(2))

    # ③ asyncio.ensure_future() —— 兼容旧代码，接受 Future 或协程
    task3 = asyncio.ensure_future(work(3))

    print(await task1, await task2, await task3)
注意：create_task 要求传入协程对象，且会立即安排调度（不是立即执行，而是进入事件循环就绪队列，等当前协程让出后才会真正运行）。这就是"并发"的起点。

3.3 Task 核心 API

API说明
task.done()是否已完成（正常或异常结束）
task.result()获取结果；未完成抛 InvalidStateError；异常则抛该异常
task.cancel()取消任务，返回 True（若取消成功）
task.cancelled()是否已被取消
task.add_done_callback(cb)完成时自动调用回调

3.4 Task 生命周期与取消

取消任务示例
async def long_task():
    try:
        await asyncio.sleep(5)
        return "OK"
    except asyncio.CancelledError:
        print("任务被取消")
        raise          # ⚠ 必须 re-raise，否则取消会被吞掉

async def main():
    task = asyncio.create_task(long_task())
    print(task.done())       # False
    await asyncio.sleep(1)
    task.cancel()            # 1秒后取消
    try:
        await task
    except asyncio.CancelledError:
        print("捕获取消异常")
    print(task.cancelled())   # True
False 任务被取消 捕获取消异常 True

task = asyncio.create_task(asyncio.sleep(1))
await task   # 等待完成
await task   # 立即返回 None，不会报错
为什么 Task 能多次 await？因为 Task 是 Future 的子类，结果被存在 Future 里。第一次 await 后结果就固定了，后续 await 直接返回缓存的结果。而协程对象没有"结果缓存"概念，await 一次就消费完了。

4Future 详解

4.1 Future 的设计初衷

Future 是低层级可等待对象，代表"异步操作的最终结果"（可能还未就绪）。它专为 asyncio 事件循环设计，类似但不等于 concurrent.futures.Future。

典型场景：当你写一个异步库时，需要返回一个可等待对象，但内部操作不是协程（比如底层用回调或 socket）。你就创建一个 Future，在操作完成时调用 future.set_result()，使用者就能 await future。
图 4-1　Future 的工作机制：占位 → 等待 → 外部设置结果 → 唤醒

4.1.1 为什么需要 Future？——回调转异步实战

很多开发者卡在"什么时候才需要手动用 Future"。核心判断标准：你写的东西内部不是协程，但对外想提供 await 接口。下面三个例子从简到繁，完整还原这个场景。

核心矛盾：有些底层操作不是协程——loop.call_later(cb) 是回调式、老式 socket 库是回调式、第三方 C 库绑定也是回调式。你没法 await 它们。但你的用户想写 result = await your_func()。Future 就是这个"翻译器"：回调触发时 set_result 往盒子里放值，使用者 await 从盒子里取值。
图 4-2　Future 作为"回调世界 → 异步世界"的翻译器

例 1：把定时器回调包装成可 await（最简版）

loop.call_later(delay, callback) 是回调式 API：到点后调用 callback，但不返回值给你。我们用 Future 把它变成可 await 的协程。

例1：定时器回调 → 可 await
import asyncio

# === 库作者视角：内部用回调，对外提供 await ===
async def async_delay(seconds):
    """底层用回调式 call_later，但对外是可 await 的协程"""
    loop = asyncio.get_running_loop()
    fut = loop.create_future()        # ① 创建空盒子（pending）

    def on_timer():               # ② 定义回调（普通函数，不是协程）
        fut.set_result("时间到")    # ③ 回调触发时，往盒子里放值

    loop.call_later(seconds, on_timer)   # ④ 注册回调（立即返回，不阻塞）
    return await fut               # ⑤ 使用者 await 取值（盒子空时就挂起）

# === 使用者视角：和普通协程用起来一模一样 ===
async def main():
    print("开始")
    result = await async_delay(1)     # 体验等同 await asyncio.sleep(1)
    print(result)                  # "时间到"

asyncio.run(main())
开始 （1秒后）时间到
关键理解：async_delay 内部根本没用 asyncio.sleep，它用的是回调式 call_later。但因为有了 Future 桥接，使用者完全感知不到——他只看到一个普通协程。这就是 Future 的价值：让回调式底层拥有协程式的调用体验。

例 2：把回调式 socket 包装成可 await

很多底层网络库（旧版 socket、某些 C 库绑定）是基于回调的。数据到达时调用 callback(data)，但你没法 await 它。用 Future 包装：

例2：回调式 socket → 可 await
import asyncio

# === 假设这是底层 socket 库：基于回调，不是协程 ===
class FakeSocket:
    """模拟回调式 socket：数据到达时调用 callback"""
    def recv(self, callback):
        # 注意：这个方法不是 async！注册回调后立即返回
        loop = asyncio.get_running_loop()
        loop.call_later(0.5, callback, b"hello from socket")

# === 库作者：用 Future 把回调式 socket 翻译成可 await ===
async def async_recv(sock):
    loop = asyncio.get_running_loop()
    fut = loop.create_future()        # ① 创建空盒子

    def callback(data):
        if not fut.done():
            fut.set_result(data)     # ② 数据到达 → 放进盒子

    sock.recv(callback)              # ③ 注册回调（不 await，立即返回）
    return await fut                 # ④ 等盒子有值

# === 使用者：完全不用关心回调 ===
async def main():
    sock = FakeSocket()
    print("准备读取...")
    data = await async_recv(sock)      # 用起来和普通协程一样
    print(f"收到: {data}")            # b"hello from socket"

asyncio.run(main())
准备读取... （0.5秒后）收到: b'hello from socket'
为什么要 if not fut.done() 检查？因为回调可能被多次触发（比如 socket 多次收到数据），但 Future 只能 set_result 一次，第二次会抛 InvalidStateError。加这个检查是防御性编程。

例 3：把第三方回调 API 包装成异步（含异常处理，最实用）

真实场景：你用了一个第三方库（数据库驱动、C 库绑定），它只支持回调，有成功回调和错误回调。用 Future 包装后，使用者甚至能用 try/except 捕获异常。

例3：第三方回调 API → 可 await（含异常）
import asyncio

# === 假设这是第三方库：只支持回调 ===
def query_db(sql, callback, error_callback):
    """执行 SQL，成功调 callback(result)，失败调 error_callback(err)"""
    loop = asyncio.get_running_loop()
    def do_query():
        if "BAD" in sql:
            error_callback(ValueError("SQL 语法错误"))
        else:
            callback(f"查询结果: {sql}")
    loop.call_later(0.3, do_query)

# === 你来包装：回调式 → 可 await ===
async def async_query(sql):
    loop = asyncio.get_running_loop()
    fut = loop.create_future()

    def on_success(result):
        if not fut.done():
            fut.set_result(result)       # 成功 → 放结果

    def on_error(err):
        if not fut.done():
            fut.set_exception(err)       # 失败 → 放异常（await 时会抛出）

    query_db(sql, on_success, on_error)   # 注册回调
    return await fut                     # 等 result 或 exception

# === 使用者：像普通 async 函数一样用，还能 try/except ===
async def main():
    # 正常查询
    result = await async_query("SELECT * FROM users")
    print(result)                       # 查询结果: SELECT * FROM users

    # 异常查询 —— 可以 try/except 捕获！
    try:
        await async_query("BAD SQL")
    except ValueError as e:
        print(f"捕获异常: {e}")       # 捕获异常: SQL 语法错误

asyncio.run(main())
（0.3秒后）查询结果: SELECT * FROM users 捕获异常: SQL 语法错误
例 3 的精髓：set_exception 让回调式 API 的错误也能被 await 方用 try/except 捕获。使用者完全感觉不到底层是回调式的——他写的是 await 和 try/except，但底层其实是回调 + Future 翻译。这就是"异步库开发"中 Future 的核心用途。

三步公式（背下来）

写一个"回调转异步"的包装函数，永远三步： 1. fut = loop.create_future() # 创建空盒子 2. 注册回调；回调里 fut.set_result(data) # 回调触发时放值 3. return await fut # 使用者取值 异常版：失败时用 fut.set_exception(err) 代替 set_result

4.1.2 常见误区：Future 能把同步转异步吗？

正确答案：不能。Future 转换的是"回调式异步 → await 式异步"，不是"同步阻塞 → 异步非阻塞"。它改的是编程风格，不是阻塞性质。

很多初学者学完 4.1 的回调转异步后，会产生一个危险的误解："既然 Future 能把回调变成 await，那我把阻塞代码包进 Future 也能变成异步吧？"——大错特错。下面用代码证明。

反例：Future 救不了阻塞代码

❌ 错误示范——拿 Future 包装 time.sleep，照样卡死事件循环
import asyncio, time

async def bad_wrapper():
    loop = asyncio.get_running_loop()
    fut = loop.create_future()

    # time.sleep 是同步阻塞调用——它占着当前线程死等 5 秒
    # 这 5 秒期间，事件循环完全冻结，任何其他协程都得不到执行
    time.sleep(5)
    fut.set_result("done")   # 5 秒后才设置结果，太晚了

    return await fut           # 包了 Future 也毫无意义

async def heartbeat():
    # 这个协程本该和 bad_wrapper "并发"运行
    # 但因为 time.sleep 卡死了事件循环，心跳也一起冻住
    for i in range(5):
        print(f"  心跳 {i}")
        await asyncio.sleep(1)

async def main():
    await asyncio.gather(bad_wrapper(), heartbeat())

asyncio.run(main())
# 输出：卡死 5 秒，期间没有心跳，5 秒后才打印
运行结果解读
整个程序静默 5 秒，heartbeat 的"心跳 0"也不打印。
5 秒结束后，5 条心跳和"done"才一起刷出来。
这说明 Future 根本没有改变 time.sleep 的阻塞性质——它照样霸占线程、冻死事件循环。

正例：Future 正确的使用场景——回调式 API（本来就是异步的）

✅ 正确用法——loop.call_later 本来就是非阻塞的，Future 只是让写法更好
async def good_wrapper():
    loop = asyncio.get_running_loop()
    fut = loop.create_future()

    # loop.call_later 本身就 不阻塞——它只是注册一个定时器回调
    # 注册完立刻返回，事件循环继续运转，2 秒后才调 on_timer
    def on_timer():
        fut.set_result("timer 触发")

    loop.call_later(2, on_timer)   # 注册回调，立即返回

    return await fut   # 挂起等结果，这 2 秒事件循环干别的活儿

# heartbeat 可以正常心跳，因为 call_later 没有阻塞事件循环

这里的 call_later 本来就是非阻塞的——它底层用的是系统定时器中断，不占用运行时间。Future 只是让你能用 await 这种好看写法拿到结果，而不是嵌套回调。阻塞还是阻塞，非阻塞还是非阻塞——Future 对此没有改变。

那"真正的同步转异步"靠谁？——run_in_executor（线程池）

✅ 真正把阻塞代码变成"不卡事件循环"的方法
import requests

async def real_sync_to_async(url):
    loop = asyncio.get_running_loop()

    # requests.get 是阻塞的，但被丢进线程池跑
    # 主线程的事件循环完全不受影响，其他协程照常执行
    resp = await loop.run_in_executor(
        None,                # None = 用默认线程池 (ThreadPoolExecutor)
        requests.get,       # 要在线程里执行的阻塞函数
        url                  # 传给阻塞函数的参数
    )
    return resp.status_code
run_in_executor 的底层也是 Future
线程池在另一个线程里跑 requests.get，跑完把结果 set_result 到 Future 里，主协程 await 拿到。
但"把阻塞变非阻塞"的功劳是线程池的，不是 Future 的。Future 只负责把线程的结果传回协程。
换句话：线程池干了"让阻塞不卡主线程"的活，Future 干了"把线程结果送回协程"的活。

三句话总结

这件工具转换了什么阻塞 → 非阻塞？
Future回调式写法 → await 写法❌ 不改变（回调本来就不阻塞）
run_in_executor同步阻塞调用 → 丢进线程池✅ 真正改变（不卡主线程的事件循环）

记忆口诀：Future 换写法，run_in_executor 换线程。两个配合用才是完整的"回调→async→async 内跑阻塞"流水线。

5同步转异步 —— 原理与实战

前面 4.1.2 说了 Future 不能把同步变异步。那什么可以？答案是线程池（run_in_executor）。本章从事件循环的单线程本质讲起，拆解线程池如何在不阻塞主循环的前提下执行同步代码，以及背后 set_result + call_soon_threadsafe 的协作机制。

5.1 为什么需要"同步转异步"？

asyncio 的事件循环运行在单一主线程里。它像一个调度员，轮流把 CPU 时间片分给各个协程：A 跑一会、A 挂起等 I/O、B 跑一会、B 挂起……只要每个协程都"跑一会就主动交出控制权（await）"，整个系统就能保持流畅。

但现实中大量库是同步阻塞的——requests.get()、openpyxl.load_workbook()、time.sleep()、数据库驱动……它们一跑就是一口气跑到结束，期间绝不让出控制权。于是你的事件循环被卡死，整个程序冻结。

所以，同步转异步的实质是：在不修改第三方库代码的前提下，把阻塞调用搬出主线程，让事件循环可以继续运转。这就得靠 asyncio 内置的线程池机制。

5.2 底层原理：事件循环 + 线程池协作模型

先看图建立直觉，再看源码分解。

图 5-1　事件循环单线程模型 vs 线程池卸载模型

核心流程（四步走）：

step 1：提交——协程调用 loop.run_in_executor(executor, blocking_func, *args)，事件循环把任务提交给线程池，立即返回一个 Future。
step 2：卸载——线程池分配一个空闲线程，在该线程里执行阻塞函数。主线程的事件循环完全不受影响，继续调度其他协程。
step 3：结果回传——阻塞函数执行完毕，线程调用 future.set_result(value)。但 set_result 内部 不能直接从子线程操作事件循环，所以用了 loop.call_soon_threadsafe 把"唤醒等待者"这件事注册成主线程的下一个回调。
step 4：唤醒——事件循环在下一轮调度时执行该回调，等待该 Future 的协程被唤醒，拿到结果继续往下跑。

run_in_executor 的核心逻辑非常简单：把阻塞函数丢进 concurrent.futures 的线程池，线程跑完后用 call_soon_threadsafe 把 set_result 调回主线程。整套机制不到 30 行，但设计精妙——它是 asyncio 世界里引入多线程的唯一官方出口。

5.3 方案一：run_in_executor——最常用

把阻塞的 requests 变成不卡事件循环的 await
import asyncio
import requests
from concurrent.futures import ThreadPoolExecutor

async def fetch_url(url):
    loop = asyncio.get_running_loop()
    # 用默认线程池（None），requests.get 在子线程里跑
    resp = await loop.run_in_executor(
        None,            # None = 默认线程池，线程数基于 CPU 核数
        requests.get,   # 阻塞函数（传引用，不要调用了再传）
        url              # 阻塞函数的参数，可以传多个
    )
    return resp.status_code

async def main():
    urls = ["https://httpbin.org/delay/2"] * 10
    # 10 个请求并发，总共约 2 秒完成（不是 20 秒）
    tasks = [fetch_url(u) for u in urls]
    results = await asyncio.gather(*tasks)
    print(results)
可以指定自定义线程池来控制并发上限
executor = ThreadPoolExecutor(max_workers=5)
然后传给 run_in_executor(executor, ...)。当并发量大时，限制线程数避免资源耗尽。

5.4 方案二：asyncio.to_thread（Python 3.9+ 语法糖）

如果阻塞函数只有一个参数或者没参数，to_thread 比 run_in_executor 更简洁：

底层是一样的：to_thread 内部就是调了 loop.run_in_executor(None, func, *args)。它永远用默认线程池，不支持自定义线程池。如果需要控制线程数，还是得用 run_in_executor。

5.5 方案三：ProcessPoolExecutor——CPU 密集型

线程池有个致命限制——Python 的 GIL（全局解释器锁）。如果是纯 Python 的 CPU 计算（如图像处理、数据清洗），多线程并不能真正并行，因为同一时刻只有一个线程能执行 Python 字节码。这时要用进程池：

CPU 密集型用进程池（绕过 GIL）
from concurrent.futures import ProcessPoolExecutor
import time

def cpu_heavy(n):          # 注意：必须是普通函数，不能是 async
    total = 0
    for i in range(n):
        total += i ** 0.5       # 纯 Python CPU 计算，线程池帮不上忙
    return total

async def main():
    loop = asyncio.get_running_loop()
    with ProcessPoolExecutor(max_workers=4) as pool:
        tasks = [
            loop.run_in_executor(pool, cpu_heavy, 50000000)
            for _ in range(4)
        ]
        results = await asyncio.gather(*tasks)
    print(results)   # 4 个进程真正并行计算，总时间约等于单次
进程池的代价：每个进程需要序列化参数（pickle）传给子进程、反序列化结果传回来。如果数据量很大或函数很短，序列化开销可能超过计算收益。只有计算量远大于通信量的场景才值得用。

5.8 注意事项与常见陷阱

陷阱一：在线程里直接操作 Future —— 它线程不安全
Future、Task、asyncio.Queue 等对象不是线程安全的。它们的内部状态（回调列表、结果标记）没有任何锁保护。 直接在线程里调用 future.set_result() 会导致回调在错误线程执行、内部状态竞争、甚至死锁。

为什么会不安全？——看 Future 的源码就懂了

Future 内部的 _callbacks 是一个普通 Python 列表：

Future 内部简化——没有锁，没有线程保护
class Future:
    def __init__(self):
        self._callbacks = []      # 普通 list，多线程同时 append/pop 会崩
        self._result = None
        self._state = "PENDING"   # 多线程同时读写 = 竞态条件

    def set_result(self, result):
        if self._state != "PENDING":
            raise InvalidStateError   # 无锁判断，竞态下可能漏掉
        self._result = result
        self._state = "FINISHED"
        for cb in self._callbacks:  # 直接在调用线程执行回调！
            cb(self)                   # 如果回调里操作事件循环 = 灾难
三个致命问题：
1. 回调执行线程不对——set_result 在子线程调，回调 cb(self) 也在子线程执行。如果回调里操作了事件循环（比如 schedule 新协程），事件循环对象本身也不是线程安全的——崩溃。
2. 回调列表竞态——一边遍历 _callbacks 一边另一个线程往里 append，Python 的迭代器直接抛 RuntimeError: list changed size during iteration，丢回调。
3. 状态读写竞态——两个线程同时检查 _state == "PENDING"，同时通过，同时设结果。第二个 set_result 应该抛 InvalidStateError，但因为无锁，它可能直接覆盖了第一个结果。
这些 bug 不是每次都重现，压力一大就随机炸——最头疼的那种。

错误示范：直接在线程里 set_result

❌ 这段代码有时候能跑，有时候崩溃——取决于线程调度的运气
import asyncio, threading, time

async def main():
    loop = asyncio.get_running_loop()
    fut = loop.create_future()

    def worker():                              # ← 这个函数在子线程里跑
        time.sleep(1)
        fut.set_result("线程结果")           # ← 在子线程里调 set_result！

    t = threading.Thread(target=worker)
    t.start()

    def on_done(f):                            # ← 被 set_result 内部触发,在子线程里跑！
        loop.call_soon(print, "拿到结果") # ← 从子线程调 call_soon,不是线程安全的

    fut.add_done_callback(on_done)
    result = await fut
    print(result)
    t.join()

asyncio.run(main())
逐行追踪——到底谁在哪个线程运行？
时刻代码运行线程为什么危险
1 t.start() 主线程 创建子线程，安全
2 fut.set_result(...) 子线程 从子线程直接操作 Future，不安全
3 set_result 内部遍历 _callbacks 子线程 主线程可能同时在 add_done_callback 写这个列表 → 竞态
4 cb(self) → 调用 on_done(f) 子线程 回调跑到子线程去了！
5 loop.call_soon(print, ...) 子线程 call_soon 直接操作事件循环的 _ready 队列（非线程安全）
主线程正在迭代同一个队列 → 数据损坏/崩溃

核心问题是第 5 步。下面展开讲为什么 call_soon 被从子线程调用会"爆炸"：

call_soon 内部——没有锁,直接追加到事件循环的就绪队列
class BaseEventLoop:
    def call_soon(self, callback, *args):
        handle = Handle(callback, args, self)   # 包装成 Handle 对象
        self._ready.append(handle)           # ← 直接 append，没有锁！
        return handle

# 而事件循环的主循环里同时在这样消费 _ready 队列：
    def _run_once(self):
        ...
        ntodo = len(self._ready)
        for i in range(ntodo):
            handle = self._ready.popleft()      # ← 也在操作同一个队列！
            handle._run()
        ...

换句话说：事件循环的主线程正在从 _ready 队列里取出 Handle 执行（popleft），而子线程同时往同一个队列追加（append）。collections.deque 的 append 和 popleft 并发执行时内部指针会错乱，导致数据损坏、元素丢失、甚至段错误。没有锁的并发读写 = 未定义行为。

但 call_soon_threadsafe 就不一样——它用锁保护了跨线程访问：

call_soon_threadsafe——有锁,跨线程安全
    def call_soon_threadsafe(self, callback, *args):
        handle = Handle(callback, args, self)
        with self._scheduled_lock:              # ← 加锁！
            self._ready.append(handle)
        self._write_to_self()                  # 通过 self-pipe 唤醒事件循环
        return handle
总结链式反应：子线程调 set_result → set_result 内部同步执行回调 cb(self) → 每个回调都在子线程里跑 → 回调里如果调 call_soon / create_task → 无锁操作事件循环内部队列 → 与主线程的并发读写冲突 → 数据损坏/崩溃/静默丢任务。

唯一解法：子线程永远不直接调 set_result，而是用 call_soon_threadsafe 把它投递回主线程。

正确做法：call_soon_threadsafe 把操作投递回事件循环

✅ 唯一正确的跨线程路径——让事件循环自己来 set_result
async def main_safe():
    loop = asyncio.get_running_loop()
    fut = loop.create_future()

    def worker():
        time.sleep(1)
        # ✅ 正确：不直接调 set_result，而是把 set_result 注册成
        #    事件循环的下一个回调，让主线程来执行
        loop.call_soon_threadsafe(fut.set_result, "线程结果")
        # call_soon_threadsafe 内部用了 self-pipe 或 eventfd
        # 从子线程安全地"唤醒"事件循环，并排队这个回调

    t = threading.Thread(target=worker)
    t.start()

    result = await fut       # set_result 在事件循环线程执行，安全
    print(result)
    t.join()
call_soon_threadsafe 做了什么？
1. 用一个线程安全的队列（_ready deque + 互斥锁）接收跨线程投递的回调
2. 通过 self-pipe（Unix）或 IOCP（Windows）向事件循环发信号："有新货了，起来干活"
3. 事件循环在下一轮 _run_once 里检查这个队列，取出回调，在主线程里安全执行
这样 set_result 以及它触发的所有回调都在事件循环的主线程里跑，线程安全。
一句话：loop.call_soon_threadsafe(fut.set_result, value) 是 asyncio 世界里唯一从子线程操作 Future 的正确方式。记住这个 API。
陷阱一之延伸：run_in_executor 内部已经帮你做对了
需要区分：你用 run_in_executor 时，它内部自动调了 call_soon_threadsafe，你不需要手动处理。但如果你自己创建线程并想让结果返回事件循环——那上面这段就是必修课。
陷阱二：把 awaitable 传给 run_in_executor
await loop.run_in_executor(None, asyncio.sleep, 1)——这不会报错，但也不会按你想的跑。
asyncio.sleep 返回的是协程对象，不是阻塞函数。在线程里 await 一个协程没有意义（没有事件循环）。
规则：run_in_executor 只接普通同步函数，不接 async/协程。
陷阱三：忘记控制线程池的并发上限
用默认线程池时，线程数会随任务量自动增加，没有上限。如果一次性提交 1000 个阻塞任务，默认线程池可能创建上百个线程，每个线程做网络请求……CPU 全花在线程切换上了。
解法：自定义 ThreadPoolExecutor(max_workers=N)，一般 N 取 10-50 足够。
陷阱四：线程池 + asyncio.gather 不是银弹
如果用 gather 启动 1000 个协程，每个协程都调用 run_in_executor，任务会被排队——线程池同时只能跑 max_workers 个，剩下的在队列里等着。
这件事本身没问题，但要注意：如果你的阻塞函数需要某个外部资源（如数据库连接），而连接池只有 20 个连接，那就得用 Semaphore 配合，而不是只靠线程池限制。

6.1 yield 实现原理 —— 协程暂停与恢复的基石

为什么要把 yield 放在"源码关系与调度机制"的第一节？
前面六章讲了协程 await 就暂停、Task._step 用 send() 推进协程。但这一切的底层机制全来自 yield。不理解 yield，_step 的源码就是天书。所以先讲清楚 yield 怎么暂停和恢复，再回头看 _step 和事件循环调度，一切就通了。

普通函数 vs 生成器函数：一道分水岭

一个 yield 改变了函数的所有行为
def normal():
    return 1

def generator():
    yield 1
    yield 2
    return 3

# 普通函数：调用即执行
r = normal()      # r = 1，函数已执行完毕，调用栈已清空

# 生成器函数：调用返回"生成器对象"，函数体一行都没执行！
g = generator()     # g 是一个 generator 对象，函数体还没开始跑
next(g)               # => 1   （执行到第一个 yield，暂停）
next(g)               # => 2   （从上次暂停处继续，执行到第二个 yield，再暂停）
next(g)               # => StopIteration: 3  （执行到 return，抛 StopIteration）

两者的本质区别在于——普通函数执行完就消失了；生成器函数可以在执行到一半时暂停，保留所有局部变量和执行位置，过一段时间再从同一个地方继续。

帧（frame）对象 —— 生成器暂停的秘密

Python 在执行任何函数时，都会在 C 层创建一个 帧对象（frame object），它记录了：

  • f_lasti —— 指令指针：当前执行到了字节码的哪一条指令（整数偏移量）
  • f_locals —— 局部变量表：函数内所有变量的当前值
  • f_lineno —— 当前行号
  • f_back —— 调用者的帧（形成调用链）
  • f_valuestack —— 值栈（evaluation stack）：字节码指令的中间计算结果

字节码层面：yield 到底做了什么

Python 执行时，源码先被编译成字节码，每个字节码指令操纵一个值栈（evaluation stack）。看一个具体例子：

一个简单生成器的字节码
# Python 源码
def gen():
    x = 10
    y = yield x           # key line!
    print(y)

# 用 python -m dis gen 查看字节码：
#   0 LOAD_CONST  1 (10)
#   2 STORE_FAST  0 (x)      ; x = 10
#   4 LOAD_FAST   0 (x)      ; 把 x 的值 (10) 压入值栈
#   6 YIELD_VALUE             ; ★ 关键指令：弹出栈顶值(10)，返回给调用者，暂停帧
#   8 STORE_FAST  1 (y)      ; ★ 恢复后从这里继续：把 send() 传入的值存到 y
#  10 LOAD_GLOBAL 0 (print)
#  12 LOAD_FAST   1 (y)
#  14 CALL_FUNCTION 1
#  16 POP_TOP
#  18 LOAD_CONST  0 (None)
#  20 RETURN_VALUE

YIELD_VALUE 指令做了三件事：

  1. 从值栈弹出栈顶值（这里是 10），作为 next() 或 send() 的返回值
  2. 把当前指令指针 f_lasti 保存为 YIELD_VALUE 的下一条指令（偏移量 8）
  3. 暂停帧：把帧从执行状态标记为暂停态，控制权归还调用者

下次 next(g) 或 g.send(value) 时，Python 从 f_lasti=8 处恢复执行——也就是 STORE_FAST 1 (y)。注意：如果你用的是 g.send(20)，那么 20 会代替 YIELD_VALUE 弹出值的位置，成为 yield 表达式的求值结果。

send(value) 如何向暂停点传入值

这是初学者最容易卡的：y = yield x 这行代码到底怎么工作？分两步理解：

y = yield x 的两阶段
# 第 1 阶段：next(g) 或 g.send(None) —— 启动生成器，执行到 yield
g = gen()
r = next(g)          # 执行到 yield x
#   → YIELD_VALUE 弹出 x=10，返回给调用者
#   → r = 10
#   → 帧暂停在 STORE_FAST 1 (y) 之前（即 f_lasti = 8）

# 第 2 阶段：g.send(20) —— 向暂停点"注入"值，并继续执行
r2 = g.send(20)
#   → Python 把 20 作为 yield 表达式的值
#   → 从 f_lasti=8 恢复：STORE_FAST 1 (y)，y = 20
#   → 继续执行 print(y)，打印 20
#   → 函数末尾 → StopIteration
关键：send() 的参数替换了"yield 表达式"的求值结果。

y = yield x 可以拆成两步理解：
① 从里到外：yield 先把 x 的值"交出去"（给调用者）
② 从外到里：send() 的参数"注进来"，成为整个 yield 表达式的值，赋给 y

用快递做个类比：yield x = 把包裹 x 寄出去；send(20) = 收一个回执包裹 20，存到 y。

StopIteration 是怎么产生的

当生成器的代码执行到 return value 或自然到达函数末尾时，Python 抛出 StopIteration，异常的 .value 属性就是 return 的值（没有 return 则为 None）：

协程 return 在底层就是 StopIteration
async def foo():
    return 42

c = foo()              # 协程对象
try:
    c.send(None)         # 推进协程
except StopIteration as e:
    print(e.value)        # => 42

这就是 Task._step 里 except StopIteration as e: self.set_result(e.value) 的底层原理——协程 return 就是抛出 StopIteration，Task 捕获后把值存进 Future，完成整个链路。

yield 与 await 的关系

Python 3.5 之前，协程用 @asyncio.coroutine 装饰器和 yield from 实现。3.5 引入了 async/await 关键字，但底层仍然使用 yield 机制：

await 在字节码层面的等价转换
# 你写的：                     # 编译器生成（概念等价）：
async def fetch():          async def fetch():
    data = await fut          #  →    data = yield from fut.__await__()
    return data                #  →    return data

# await fut 的底层：
# 1. 调用 fut.__await__() 获取迭代器
# 2. 用 yield from 驱动这个迭代器
# 3. 迭代器内部 yield 出 Future → 控制权回到事件循环
# 4. Future 完成后 → send() 把结果注入 → data 拿到值

实际上，await 在 CPython 字节码中对应 GET_AWAITABLE + YIELD_FROM 两条指令，YIELD_FROM 就是 yield 的扩展版本。

总结：yield 是 asyncio 协程的基石

生成器函数 = 可以暂停和恢复的函数（靠帧的 f_lasti 保存指令指针）
yield = 暂停点 + 值出口（值出去给调用者，帧挂起）
send(value) = 恢复点 + 值入口（值注入到 yield 表达式结果，帧继续）
return → StopIteration = 完成的信号（Task 捕获后 set_result）
await → YIELD_FROM = yield 的高级版本（自动驱动子迭代器）

接下来看 Task._step，你会发现它不过是在这层 yield 机制上封装了一个调度循环。

6.2 事件循环的本质：一个单线程 dequeue 管理者

先看最核心的认知——事件循环简化到极致，就是这样一个循环：

事件循环的最简模型（概念代码，非真实源码）
# ready_queue 是 collections.deque，存放待执行的回调
ready_queue = deque()

while True:
    # ① 检查定时器堆：如果有到期的 timer，把它的回调放入 ready_queue
    while timer_heap and timer_heap[0].deadline() <= now():
        callback = heappop(timer_heap).callback
        ready_queue.append(callback)

    # ② 从 ready_queue 取一个回调执行
    if ready_queue:
        callback = ready_queue.popleft()
        callback()          # 在当前线程同步执行！
        continue

    # ③ 如果没有任何可做的事，休眠到最近一个 timer 到期
    #    （或者阻塞在 IO selector 上等数据）
    if timer_heap:
        sleep_until(timer_heap[0].deadline)
    else:
        break   # 什么都没有了，事件循环退出
三个关键结论：
① 单线程——所有 callback 都在同一个线程里顺序执行，不存在真正的"同时执行"。
② 协作式调度——一个 callback 执行完（或遇到 await 挂起），才能轮到下一个。如果某个 callback 写了 time.sleep(10)，后面所有人的 callback 都干等。
③ FIFO 就绪队列——先调度进 ready_queue 的 callback 先执行。

推论：任何一个 Task 的 _step() 方法，本质上就是一个被放入 ready_queue 的 callback。事件循环不区分"Task"和"普通回调"，它只知道从队列里取出一个函数然后调用它。

6.3 从 create_task 到执行：完整链路追踪

用一个最简单的程序来追踪全过程：

分析目标
import asyncio

async def hello():
    print("Hello")
    await asyncio.sleep(1)
    print("World")
    return 42

async def main():
    task = asyncio.create_task(hello())    # --- 第 1 步 ---
    result = await task                     # --- 第 5 步 ---
    print(result)

asyncio.run(main())

下面按时间线逐步追踪。每一步都标注了哪个协程在运行、ready_queue 里有什么、谁在 sleep 等待。

时间线追踪 —— 从 asyncio.run(main()) 到程序结束

第 1 步：asyncio.run(main()) → Task.__init__

asyncio.run 内部发生了什么
def run(main):
    loop = new_event_loop()               # 创建事件循环
    task = Task(main(), loop=loop)        # 关键：把 main() 协程包成 Task
    # Task.__init__ 里调了 loop.call_soon(task._step)
    # 所以 task._step 被放入 ready_queue
    loop.run_forever()                    # 启动事件循环主循环
此时状态：
ready_queue: [main._step]
正在运行: 无（事件循环刚要启动）
sleep 中: 无

第 2 步：事件循环取出 main._step 执行

事件循环从 ready_queue 取到 main._step，调用它。_step 内部执行 self._coro.send(None)，于是 main() 协程开始运行——执行到 task = asyncio.create_task(hello())。

create_task 内部
def create_task(coro):
    task = Task(coro, loop=loop)
    # Task.__init__ 里面又调了 loop.call_soon(task._step)
    # 于是 hello._step 也被放入 ready_queue！
    return task
此时状态：
ready_queue: [hello._step]
正在运行: main() 协程（还在执行中，没遇到 await）
sleep 中: 无

注意：hello._step 虽然已经在 ready_queue 里了，但 不会立即执行。因为 main() 协程还在跑，事件循环必须等当前的 callback（即 main._step）执行完毕才能处理队列里的下一个。

第 3 步：main() 执行到 await task

await task 的底层行为：

await task 的等效伪代码
# await task 背后发生的事情：
yield task     # 协程让出控制权，把 task（一个 Future）返回给 _step
# _step 收到 task（是一个 Future 实例），执行：
# task.add_done_callback(self._wakeup) → 注册回调
# return  → _step 结束，控制权还给事件循环
此时状态：
ready_queue: [hello._step]
正在运行: 无（main._step 已 return）
sleep 中: 无
待唤醒: main 的 _wakeup 已注册为 task 的 done_callback（等 task 完成时触发）

第 4 步：事件循环取出 hello._step 执行

hello() 协程开始运行：打印 "Hello"，然后遇到 await asyncio.sleep(1)。

await asyncio.sleep(1) 内部发生了什么
async def sleep(delay):
    fut = loop.create_future()          # 创建一个 Future
    loop.call_later(delay, fut.set_result, None)
    # call_later 把 (到期时间=now+1s, callback=fut.set_result) 放入 timer_heap
    return await fut
    # await fut → yield fut → _step 收到 fut（是 Future）→ fut.add_done_callback(_wakeup)
    # → _step 返回 → 控制权还给事件循环
此时状态：
ready_queue: []（空了！）
正在运行: 无
timer_heap: [(deadline=T+1s, callback=fut.set_result)]
待唤醒: hello 的 _wakeup 注册为 sleep_fut 的 done_callback；
         main 的 _wakeup 注册为 task 的 done_callback
这是最关键的时刻：ready_queue 空了！ 事件循环没有回调可执行了，于是进入"等待模式"——计算最近的 timer 到期时间（T+1s），调用 sleep() 或 select() 睡掉这段时间。CPU 完全不忙，这就是异步 I/O 高效的原因。

第 5 步：1 秒后，timer 到期

定时器触发链
# timer_heap 发现 sleep_fut 的 deadline 已到
# → 把 fut.set_result(None) 放入 ready_queue
# → 事件循环取出并执行 fut.set_result(None)
# → set_result 内部遍历 _callbacks，调用 hello._wakeup
# → hello._wakeup 内部：self._loop.call_soon(self.__step)
# → hello._step 被放回 ready_queue！
此时状态：
ready_queue: [hello._step]
正在运行: hello._step 即将被调度

第 6 步：hello._step 再次执行

_step 执行 self._coro.send(None)，hello() 从 await sleep 之后恢复运行——打印 "World"，然后 return 42。

return 42 在协程内部实际上抛出了 StopIteration(42)：

_step 捕获 StopIteration
except StopIteration as e:
    self.set_result(e.value)   # set_result(42)
    # set_result 遍历 hello Task 的 _callbacks，找到 main._wakeup，调用它
    # main._wakeup 内部：self._loop.call_soon(self.__step)
    # → main._step 被放回 ready_queue
此时状态：
ready_queue: [main._step]
hello Task: 已完成，result=42

第 7 步：main._step 再次执行 → main() 恢复

await task 返回结果 42，main() 继续运行——打印 "42"，程序结束。

总结这个 7 步追踪：
1. 事件循环只做一件事：从 ready_queue 取 callback 执行。
2. Task 的 _step 是"推进协程"的入口，它被 call_soon 放入 ready_queue。
3. 协程 await 时"让出"，控制权经由 _step 归还事件循环。
4. 协程 return 时抛 StopIteration，_step 捕获后 set_result 完成 Future，触发 _wakeup，_wakeup 再把 _step 放回 ready_queue。
5. 这就是一个完整的 "_step 推进 → await 让出 → Future 完成 → _wakeup → call_soon(_step) → _step 再次推进" 的闭环。

6.4 Task._step() 逐行详解

理解了整体流程后，来逐行拆解 _step。以下是 asyncio 真实源码的简化版，逐行加了注释：

Task._step 逐行详解
def _step(self, exc=None):
    # ─── 第 1 行：推进协程 ───
    try:
        if exc is None:
            result = self._coro.send(None)   # 正常推进：从上次 yield 处继续执行，直到下一个 yield/return
        else:
            result = self._coro.throw(exc)     # 异常注入：把异常抛进协程的当前暂停点

    # ─── 分支 A：协程 return → StopIteration ───
    except StopIteration as e:
        self.set_result(e.value)
        #     ↑ set_result 会做两件事：
        #     1. 把 self._state 标记为 FINISHED
        #     2. 遍历 self._callbacks，逐个调用（比如其他 Task 注册的 _wakeup）
        return

    # ─── 分支 B：协程内部抛了异常 ───
    except BaseException as e:
        self.set_exception(e)
        #     ↑ 和 set_result 类似，但 _state = EXCEPTION，_exception = e
        #     所有 await 这个 task 的地方会收到这个异常
        return

    # ─── 协程没跑完，yield 了一个值出来。_step 结束前必须决定下一步怎么唤醒 ───

    # ─── 分支 C：协程 await 了一个 Future ───
    if isinstance(result, futures.Future):
        result.add_done_callback(self._wakeup, context=ctx)
        #     ↑ 在这个 Future 上注册回调：等它完成了，就调用 self._wakeup()
        #     _wakeup 内部就是 call_soon(self.__step)，把自己放回 ready_queue
        #     这是 asyncio 链条式调度的核心机制

    # ─── 分支 D：协程 yield 了一个非 Future 值 ───
    else:
        self._loop.call_soon(self._step)
        #     ↑ 没有依赖要等，直接把自己放回 ready_queue，下次循环马上就继续
        #     这处理的是协程里 await 了一个非 Future 的 awaitable（比如自定义 __await__）

用一张图来可视化 _step 内部的四个分支：

图 6-2　Task._step() 的四个分支：A-协程完成 / B-协程异常 / C-等待 Future / D-立即重调度

很多初学者不理解为什么 await 后面接一个 Future 时，_step 的行为不同。下面是四个分支的具体例子：

四个分支的具体例子
# ===== 分支 A：协程 return → StopIteration → set_result =====
async def case_a():
    return 42
# send(None) → 协程执行 → return 42 → Python 抛出 StopIteration(42)
# → _step 捕获 → set_result(42) → Task 完成，触发所有 done_callback

# ===== 分支 B：协程内部抛异常 → set_exception =====
async def case_b():
    raise ValueError("oops")
# send(None) → 协程抛 ValueError → _step 捕获 → set_exception(ValueError)
# → 所有 await 这个 Task 的地方会收到 ValueError

# ===== 分支 C：await 一个 Future → add_done_callback =====
async def case_c():
    await asyncio.sleep(1)
# send(None) → 协程执行到 await asyncio.sleep(1) → yield 出 sleep 返回的 Future
# → _step 收到这个 Future → result.add_done_callback(_wakeup)
# → _step 返回（不重新调度自己！）→ 协程暂停，等那个 Future 完成

# ===== 分支 D：await 一个非 Future 的 awaitable（少见）=====
class CustomAwaitable:
    def __await__(self):
        yield None    # yield 出的不是 Future

async def case_d():
    await CustomAwaitable()
# send(None) → 协程 yield None → _step 收到 None（不是 Future）
# → call_soon(self._step) → 立刻重新调度，浪费一次循环但不会丢

6.5 Task._wakeup —— 重连调度的桥梁

你可能注意到，前面多次出现了 _wakeup 但还没解释它是什么。_wakeup 是 asyncio 调度机制里最容易被忽略但最关键的函数。

_wakeup 的作用
def _wakeup(self, future):
    # future 是那个"完成了"的 Future（参数由 add_done_callback 传入）
    try:
        future.result()   # 如果 future 有异常，这里会抛出——_step 会处理
    except BaseException as exc:
        self._loop.call_soon(self._step, exc)   # 带异常重新调度
    else:
        self._loop.call_soon(self._step)          # 正常重新调度
_wakeup 做了什么：被等待的 Future 完成后，Future.set_result 会遍历它的 _callbacks 列表，其中就有 task._wakeup。_wakeup 被调用后，做一件事——通过 call_soon 把 task._step 重新放回 ready_queue。于是任务"醒来"了，下次事件循环轮到它时，_step 会执行 self._coro.send(None)，协程从 await 处继续跑。

为什么需要 _wakeup 而不是直接调 _step？因为 Future 的回调可能在非主线程或 IO 回调上下文中执行，直接调 _step 会跳过事件循环的调度顺序。call_soon 保证 _step 在正确的时机（事件循环主循环中）执行。

_step 和 _wakeup 的关系可以总结为：

对比维度_step_wakeup
职责推进协程：send() 驱动协程执行到下一个 yield重新调度：把 _step 放回 ready_queue
谁调用事件循环从 ready_queue 取出后调用；或 _wakeup 通过 call_soon 间接触发Future.set_result / set_exception 遍历 _callbacks 时调用
调用时机在事件循环主循环中在某个 Future 完成的瞬间（可能在主循环中，也可能通过 call_soon_threadsafe）
是否操作协程✅ 执行 coro.send()❌ 不操作协程，只做 call_soon(self._step)
类比"开车的人""闹钟"——叫你起床，但不帮你开车

    print("B1")                     # 时刻 ③
    await asyncio.sleep(0.05)      # 时刻 ④ —— 挂起 0.05 秒（比 A 更短！）
    print("B2")                     # 时刻 ⑤ —— B 会比 A 先醒来
    return "b"

async def main():
    a = asyncio.create_task(task_a())
    b = asyncio.create_task(task_b())
    ra = await a
    rb = await b
    print(ra, rb)

asyncio.run(main())
A1 B1 B2 A2 a b

这个输出顺序经常让人困惑。下面是逐行时间线追踪，解释为什么 B2 在 A2 之前：

步ready_queue正在执行timer_heap发生了什么
1 [main._step] - 空 asyncio.run(main()) 创建 main Task，_step 入队
2 [a._step, b._step] main._step 空 main 运行到 create_task，创建 a 和 b，它们的 _step 入队。然后 main await a → main 挂起（_wakeup 注册为 a 的 done_callback）
3 [b._step] a._step 空 事件循环取出 a._step 执行 → a 打印 "A1" → await sleep(0.1) → sleep 创建 Future + 注册 timer(T+0.1s) → a 挂起（_wakeup 注册为 sleep_fut 的 callback）
4 [] b._step [T+0.1s: fut_a] 事件循环取出 b._step 执行 → b 打印 "B1" → await sleep(0.05) → 注册 timer(T+0.05s) → b 挂起。两个 Task 都睡了，ready_queue 空
5 [] 休眠中 [T+0.05s: fut_b, T+0.1s: fut_a] 事件循环算最近 timer = T+0.05s，sleep 到那时。CPU 不忙
6 [b._step] - [T+0.1s: fut_a] T+0.05s 到了！timer 触发 fut_b.set_result → _wakeup → call_soon(b._step) → b._step 入队
7 [] b._step [T+0.1s: fut_a] 事件循环取出 b._step 执行 → b 从 await 处恢复 → 打印 "B2" → return "b" → StopIteration("b") → set_result("b") → 触发 b 的 done_callback
8 [] 休眠中 [T+0.1s: fut_a] b 完成了，但没人 await b（main 还在等 a）。a 还在 wait sleep_fut_a。事件循环继续睡到 T+0.1s
9 [a._step] - 空 T+0.1s 到了！fut_a.set_result → _wakeup → call_soon(a._step)
10 [] a._step 空 事件循环取出 a._step → a 恢复 → 打印 "A2" → return "a" → set_result("a") → 触发 a 的 done_callback（main._wakeup） → call_soon(main._step)
11 [main._step] - 空 事件循环取出 main._step → main 恢复 → await a 返回 "a" → await b 立即返回（b 已完成）→ 打印 "a b" → 程序结束
关键洞察：B2 比 A2 先打印，是因为 B 的 sleep 时间（0.05s）比 A 的 sleep 时间（0.1s）短。B 先醒来，先完成。这就是异步并发的本质——不是同时执行，而是谁先准备好谁先跑。

另一点值得注意：步骤 8。B 在 T+0.05s 就完成了，但 main 还没有恢复（它在等 a）。B 的 Future 已经完成了（_state=FINISHED, _result="b"），只是结果还没被读取。这就是 Future 作为"结果缓存"的体现——你先完成，我把结果存着，你什么时候来读都行。

6.7 事件循环的调度策略总结

把整章的内容浓缩成几个核心事实：

问题答案
谁决定执行顺序？ collections.deque 类型的 ready_queue，FIFO 先进先出。call_soon(fn) 往队尾插入，popleft() 从队首取出。
谁决定 sleep 的精度？ heapq 实现的 timer_heap（最小堆），按 deadline 排序。每次主循环检查堆顶是否到期。
协程之间会互相抢占吗？ 不会。没有抢占式调度。一个协程必须遇到 await 才会让出控制权。如果一个协程写了死循环且没有 await，它会永远霸占事件循环，其他所有任务都被饿死。
create_task 后 Task 立即执行了吗？ 没有。create_task 只是把 _step 放进 ready_queue。要等当前 callback 执行完毕后，事件循环才会从队列里取出它执行。
await 到底做了什么？ 对协程来说：yield 一个 Future 给 _step。对 _step 来说：收到 Future 后 add_done_callback(_wakeup)，然后 return 归还控制权。对事件循环来说：当前的 callback 执行完毕了，去 ready_queue 找下一个。
_step 和 _wakeup 配合模式 _step → send() → await → yield Future → add_done_callback(_wakeup) → 等待 → Future 完成 → _wakeup → call_soon(_step) → 循环
协程 return 后发生了什么？ return value → Python 抛出 StopIteration(value) → _step 捕获 → set_result(value) → 遍历 _callbacks → 每个等待者（通过 _wakeup → call_soon → _step）被唤醒
一句话记住整章：
核心循环只有三步——① 从 ready_queue 取 callback ② 执行它 ③ 执行过程中，callback 可能往 ready_queue 加新 callback，也可能注册到 Future 上等待被唤醒。所有 asyncio 的调度魔法都来自这三步的排列组合。

最关键的认知：事件循环不知道什么是协程、Task、await——它只知道队列和回调。协程/Task/Future 这三个抽象是构建在这些原始机制之上的高层概念。理解了这一点，你就能看懂 asyncio 的全部源码。

7.3 Future 的超时机制 —— 别让等待变成"永远"

问题：Future 本身没有超时能力

回顾 Future 的工作方式：你创建它、await fut、等别人 set_result。但如果那个"别人"卡死、bug、或者数据永远不来呢？你的协程就永远挂在那里。

❌ 这段代码可能永远不返回
async def wait_forever():
    loop = asyncio.get_running_loop()
    fut = loop.create_future()
    # 假设某个回调式 API 应该调用 fut.set_result("数据")
    # 但如果 API 挂了、网络断了、回调没触发——
    # await fut 就会无限挂起，整个调用链卡死
    return await fut

这就是"Future 超时"要解决的问题：给等待加一个截止时间，时间到了自动打断。

方案一：asyncio.wait_for —— 最直接的方式

wait_for 接受一个 awaitable 和 timeout 秒数。超时到了，它会取消内部的 awaitable 并抛出 asyncio.TimeoutError。

wait_for 包装 Future
async def fetch_with_timeout():
    loop = asyncio.get_running_loop()
    fut = loop.create_future()     # 空盒子

    # 模拟：2 秒后才有回调 set_result
    def delayed_callback():
        # 假设这是某个第三方回调库，2 秒后才触发
        fut.set_result("网络响应数据")
    loop.call_later(2, delayed_callback)

    try:
        # 只给 1 秒等结果——注定超时
        result = await asyncio.wait_for(fut, timeout=1)
        return result
    except asyncio.TimeoutError:
        print("超时了，对方 2 秒才回应但我们只等 1 秒")
        # 可选：取消等待中的 Future，避免它后台飘着占资源
        fut.cancel()
        return None
超时了，对方 2 秒才回应但我们只等 1 秒

方案二：自己实现超时 —— 用 call_later 当倒计时

理解 wait_for 内部做了什么，比直接用它更重要。核心思路就三步：

手写超时机制的三步走
async def my_wait_for(fut, timeout):
    """自己实现 wait_for 的核心逻辑"""
    loop = asyncio.get_running_loop()

    # 第 1 步：创建一个倒计时。timeout 秒后，自动触发一个回调
    # 这个回调里：如果 fut 还没完成，就往里塞一个 TimeoutError
    timer_handle = loop.call_later(timeout, lambda: _on_timeout(fut))

    def _on_timeout(f):
        if not f.done():
            f.set_exception(asyncio.TimeoutError())  # 关键！

    try:
        # 第 2 步：正常 await。有两种可能：
        #   - fut 先完成：正常拿到结果
        #   - timeout 先到：_on_timeout 跑 set_exception，
        #     await fut 就会抛 TimeoutError
        result = await fut
        return result
    finally:
        # 第 3 步：不管超时还是完成，清理倒计时（避免定时器飘着）
        timer_handle.cancel()

# === 测试：2 秒的任务，只等 1 秒 ===
async def test_timeout():
    loop = asyncio.get_running_loop()
    fut = loop.create_future()

    # 2 秒后才 set_result——注定超时
    async def setter():
        await asyncio.sleep(2)
        fut.set_result("结果")
    asyncio.create_task(setter())

    try:
        result = await my_wait_for(fut, 1)
        print(f"拿到: {result}")
    except asyncio.TimeoutError:
        print("超时! 1 秒到了，但结果还没来")
超时! 1 秒到了，但结果还没来

本质：call_later 和 set_exception 的"赛跑"

超时的底层机制就是一场竞速：

图 7-1　Future 超时的竞速机制：谁先到，听谁的

核心就一句话：用 loop.call_later 设一个倒计时，到点了就 set_exception(TimeoutError) 到 Future 里——和正常 set_result 比速度，谁先触发，Future 就听谁的。

对比：为什么用 cors = await coro() 时不需要操心超时？

如果你 await asyncio.sleep(10)，你很清楚它 10 秒后完成。但 Future 不一样——你 不知道什么时候会完成（取决于回调何时被触发），所以才需要超时这个"兜底"。

场景需要超时保护？原因
await asyncio.sleep(1)❌ 不需要确定 1 秒后完成
await asyncio.wait_for(sleep(5), timeout=1)✅ 需要内部操作太慢，要兜底
await fut（回调式 API）✅ 需要回调可能永远不触发，必须兜底
await http_request(url)（第三方库）✅ 需要网络 I/O 不可控，超时是必须的

一个真实场景：第三方库的回调可能永不触发

用 wait_for 保护第三方回调
import asyncio

async def call_legacy_api_with_timeout(url, timeout=5):
    """包装一个老式回调库，加上超时保护"""
    loop = asyncio.get_running_loop()
    fut = loop.create_future()

    def on_response(data):
        fut.set_result(data)        # 正常路径

    def on_error(err):
        fut.set_exception(err)     # 异常路径

    # 假设 old_http_client 是个老式回调库
    # old_http_client.fetch(url, on_response, on_error)

    try:
        return await asyncio.wait_for(fut, timeout=timeout)
    except asyncio.TimeoutError:
        print(f"{url} 请求超时，{timeout}s 内回调未触发")
        fut.cancel()    # 主动取消，释放引用
        return None
一句话记住：await fut 是无期限的等；await wait_for(fut, timeout) 是限时等。如果你不确定"set_result 的调用者"是否靠谱，永远用 wait_for。

10.2 用 Future 实现可超时的操作封装

TimeoutFuture 类
class TimeoutFuture:
    """可设置超时的 Future，时间到自动设异常"""
    def __init__(self, loop, timeout):
        self._future = loop.create_future()
        self._timeout_handle = loop.call_later(timeout, self._on_timeout)

    def _on_timeout(self):
        if not self._future.done():
            self._future.set_exception(asyncio.TimeoutError)

    def set_result(self, value):
        self._timeout_handle.cancel()
        if not self._future.done():
            self._future.set_result(value)

    def __await__(self):
        return self._future.__await__()

async def main():
    loop = asyncio.get_running_loop()
    tf = TimeoutFuture(loop, 1)
    async def delayed():
        await asyncio.sleep(2)
        tf.set_result("成功")
    asyncio.create_task(delayed())
    try:
        print(await tf)
    except asyncio.TimeoutError:
        print("操作超时")

asyncio.run(main())

三条关键原则

  1. 协程是定义，Task 是调度实例，Future 是结果容器。

题目 2：协程 vs Task 生命周期观察

编写 async def show_state(duration)，用 inspect.getcoroutinestate 打印协程状态，await asyncio.sleep(duration)，再打印状态。在 main 中：创建协程对象不运行并打印状态 → 包装为 Task 打印 done() → sleep 0.1s 后再打印 → await 完成后打印最终状态。

import asyncio, inspect

async def show_state(duration):
    print("运行中:", inspect.getcoroutinestate(asyncio.current_task().get_coro()))
    await asyncio.sleep(duration)
    print("结束:", inspect.getcoroutinestate(asyncio.current_task().get_coro()))

async def main():
    coro = show_state(1)
    print("初始:", inspect.getcoroutinestate(coro))
    task = asyncio.create_task(coro)
    print("done=", task.done())
    await asyncio.sleep(0.1)
    print("0.1s后 done=", task.done())
    await task
    print("完成 done=", task.done())

题目 3：用 Future 模拟异步读

有同步 read_data(callback)，1 秒后调用回调。编写 async_read() 用 Future 适配为可 await 版本。

参考答案 
def sync_read_data(callback):
    asyncio.get_running_loop().call_later(1, callback, "Hello Future")

async def async_read():
    loop = asyncio.get_running_loop()
    future = loop.create_future()
    def callback(data):
        if not future.done():
            future.set_result(data)
    sync_read_data(callback)
    return await future

题目 4：任务取消的正确处理

编写 long_work() 循环 10 次每次 sleep 0.5s，被取消时清理并 re-raise。main 中启动任务 0.3s 后取消并捕获异常。

参考答案 
async def long_work():
    try:
        for i in range(10):
            await asyncio.sleep(0.5)
    except asyncio.CancelledError:
        print("取消中，清理资源")
        raise
    return "完成"

async def main():
    task = asyncio.create_task(long_work())
    await asyncio.sleep(0.3)
    task.cancel()
    try: await task
    except asyncio.CancelledError: print("任务已取消")

题目 5（进阶）：混合 Task 和 Future 实现并发控制器

实现 ConcurrentRunner 类，接受 max_concurrent，提供 submit(coro) 返回 Future，内部用队列和任务槽位控并发。提交 10 个耗时 1 秒的协程，最大并发 3，总耗时应约 4 秒。

参考答案 
import asyncio, time

class ConcurrentRunner:
    def __init__(self, max_concurrent):
        self._sem = asyncio.Semaphore(max_concurrent)
        self._loop = asyncio.get_running_loop()

    def submit(self, coro):
        fut = self._loop.create_future()
        async def runner():
            async with self._sem:
                try:
                    result = await coro
                    fut.set_result(result)
                except Exception as e:
                    fut.set_exception(e)
        asyncio.create_task(runner())
        return fut

async def main():
    runner = ConcurrentRunner(3)
    async def work(i):
        await asyncio.sleep(1)
        return i
    start = time.time()
    futs = [runner.submit(work(i)) for i in range(10)]
    results = await asyncio.gather(*futs)
    print(results, f"耗时 {time.time()-start:.1f}s")   # ~4s

asyncio.run(main())
